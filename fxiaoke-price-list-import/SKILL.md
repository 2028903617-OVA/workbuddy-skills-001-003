# 纷享销客物料与价目表工具

**一个技能，三个能力**。先按下面的表判断走哪条，再打开对应文档；三份文档只读需要的那份。

| # | 能力 | 用户怎么说 | 打开 | 脚本 |
|---|---|---|---|---|
| **1** | 价目表明细维护（查 + 写） | 「加进价目表」「价目表明细导入」「处理价目表」「维护一下价目表」 | `references/ability-1-pricebook-import.md` | `scripts/query_pricebook.py` |
| **2** | 我方物料匹配外部物料 | 「这些对应我们哪个物料」「我们有没有」「销客产品编码是多少」「跟我们的物料对一下」 | `references/ability-2-material-match.md` | `scripts/match_material.py` |
| **3** | 外部物料 → 我方物料名 | 「帮我生成我们内部的物料名称」「这批是新机型，系统里没有」「按我们的格式命名」 | `references/ability-3-material-name.md` | `scripts/build_new_material.py` |

**组合用法**（实际跑批常见）：外部清单 → 先走**能力 2** 匹配已有物料 → 匹配不上的再走**能力 3** 生成新物料名 → 最后走**能力 1** 查漏补缺并写进价目表明细。

## ★ 能力 1 主流程（v1.9.0 起，快照已弃用）

> 用户 2026-10-13 明确：「以后不要用快照了，直接通过连接器查找纷享销客已有的产品，然后再查看启用的价目表明细是否已有，有则直接在我确认后更新到价目明细中，没有则直接新建价目表明细，注意都是你先查，我确认要做这个动作后，你再做下一步整理好价格品牌品类品项，节约token！」

**四步，一条命令搞定「先查」和「后写」两阶段：**

```bash
# 阶段 1（默认，纯只读）—— 查到「哪些新建 / 哪些更新」，报给用户
python scripts/query_pricebook.py --source <源表.xlsx> --org <组织>

# 阶段 2（★ 用户确认后）—— 整理价格/品牌/品类/品项并直写
python scripts/query_pricebook.py --source <源表.xlsx> --org <组织> --apply
```

| 步 | 做什么 | 通道 |
|---|---|---|
| ① 查产品 | 按源表型号/名称实时搜 `ProductObj`，**候选逐级放宽**（完整串 → 型号码 token），再过两道闸（型号码边界 + 品牌一致） | 连接器（CLI `data record query-by-fields`） |
| ② 查明细 | 拿产品在该组织对应价目表里的明细（`product_id` + `pricebook_id` 双条件查重） | 同上 |
| ③ 报用户 | 逐行列：产品已存在/未同步、明细已有/未建、→ 新建/更新、待写值、品牌·大类·品项 | 文本精简输出 |
| ④ 确认后写 | 用户确认 → 整理价格·品牌·品类·品项 → 直写 | OpenAPI（`--apply` 才提交） |

**关键约束**：
- **查不到产品 ≠ 可以自己建**。系统里查不到 → 报「产品未同步」，让用户先在**金蝶**新建（见共用硬规则）。脚本对该行只输出 `产品未同步`、绝不 create。
- **`--apply` 必须等用户明确确认**（铁律 1）；脚本默认只读，不加 `--apply` 只会打印报文与「[只读] 未写入」。
- **写完必须**：回读系统核对 → 补《变更台账》→ 记当日日志。
- **★ 分类可用 `--pclass / --pitem` 覆盖**（v1.9.3 新增）：某品牌产品落在**别组织**的表里、分类该按**产品实际品类**填时用。
  例：菲斯曼前置过滤器进**大金**表 → 必须加 `--pclass 净水 --pitem 前置过滤器`，
  **否则会被大金规则改成「空调/空调」**（2026-10-16 实测：不加参数会把已填对的分类改错）。
  语义：给了任一参数即**完全接管**分类，未给的项**留空**（避免混搭）；值可传中文标签或码值（如 `--pclass 6`）。
- **旧路径仍保留**：`scripts/build_import.py` 仍可生成 12/8 列导入文件（用户明确要「给我导入文件」时才用），但不作为默认。

**为什么是 CLI 而不是 MCP 工具**：本环境 MCP 工具集只有 `data_record_query-id-by-name`（仅返回 name/id/score，**无法按「产品+价目表」精确查重、取不到价格字段**）。CLI 的 `query-by-fields` 底层即连接器服务，且支持 `select_fields` 裁剪 = **省 token**。

## 共用硬规则（三个能力都适用）

- **组织 ≠ 品牌，永远不混**：组织只决定「价目表（必填）」列（映射见 `brand-pricebooks.md`）；「品牌」列填**产品的实际品牌**，★ 取值优先级（2026-10-14 修订为**三级兜底**）：① **系统产品的「分类」路径首段**（去 `K-` / `K_` 前缀；段内含已知品牌词时取品牌词本身 —— 实测 `K-东芝坐便器` → 东芝、`K_大金` → 大金）→ ② 产品名称 / 型号匹配 `BRAND_KEYWORDS` → ③ 源表品牌列**仅兜底**。**永远不填组织名**。推断不出来 → 留空 + 记核对清单，不拿组织名顶。
- **产品主数据不得自行新建**：产品统一**先在金蝶新建、再由金蝶同步到纷享销客**；系统里查不到的产品（含判定「金蝶未同步」的行），**一律回报用户**，绝不自行 create `ProductObj`（否则与金蝶同步重复建出产品）。价目表明细只能**沿用已同步过来的产品**。
- **按表头语义定位，不写死表名与列位**：源表每次都可能不同（表头在 R1 还是 R2、列名怎么叫、加列后整体右移都遇过）。一律扫前 8 行按语义认表头，见 `field-mapping.md`。
- **我方物料名的可信度排序**（能力 2/3）：物料名称类列（99–100% 完全一致）＞ 规格型号 ＞ 型号标题（与我方物料名 0 个完全一致，只能模糊）。能用物料名称就绝不用型号标题。
- **金额列输出纯数字**：去文本、去空格、去千分位逗号；4 个价字段四舍五入取整到 0 位小数（half-up），如 423.52 → 424。
- **★ 新增列名变体必须同时改两份词表**（v1.9.2 新增，2026-10-16 实测事故）：
  `HEADER_SEMANTICS`（管**找表头行**）与 `FIELD_VARIANTS`（管**定列位**）是**两份独立词表**。
  只改前者 → 表头行认得、`col_index` 却返回 `None` → 该列被**静默丢成空值**、全程不报错。
- **★ 售价列缺失 = 立即停止**（v1.9.2 新增）：`load_source_rows` 已加护栏，识别不到售价列直接抛错
  （启欣组织豁免，因其价格列本就留空）。此前文档写了要停、代码没实现，是本次事故的真正漏洞。
- **不修改源表、不覆盖用户原件**：要写回的一律输出**副本**。
- **`pricebook_sellingprice` 是默认值表达式**：走 API / 导入通道建单一律**不会自动算**，必须**显式传**（普通默认值如 `discount=100` 才会自动带出）。见 `references/field-mapping.md`。
- **select_one 字段传码值不传 label**：`field_yy0j1__c`（产品大类）、`product_item__c`（产品品项）须转码值；脚本自动查 describe + 本地缓存 `.cache/select_one_codes.json`。
- **查重结果不得截断**：判「有没有」必须看 `returnedCount` / `totalNumber`，禁止 `tail`/`head` 抽样定论。
- **★ CLI `limit` 上限 50**：超过会 `LIMIT_EXCEEDED` 且**不执行查询、静默返回 0 条**（最易被误读成「不存在」→ 重复建）。脚本已夹紧 + 阻断码抛错；>50 条用 `cli_query_all()` 翻页。
- **写入边界**：价目表明细对象 **CLI ❌ / OpenAPI ✅ 可直写**（2026-10-13 实测落库并删回）。直写必须先报「改什么、影响哪条记录」→ 等用户二次确认 → 写完补变更台账。**不得外推到销售订单**（订单含 `DOMAIN_PLUGIN_EXISTS`/`UI_EVENT_EXISTS`，绕过会算错价，仍须页面手工录单）。
- **不擅自增删行、不改型号与价格数字、不改品牌名**。

## 运行前检查

1. 用 venv Python 运行 `scripts/check_environment.py`，得到 ready / partial / needs_setup。
2. ready 或 partial：继续；partial 时向用户说明受影响功能（见「降级与停止」）。
3. needs_setup：只展示缺失项和 `references/setup-guide.md` 对应步骤，等用户补齐后重检，不猜测继续。
4. **改动任何脚本后必须跑测试**：`test_build_import.py`、`test_match_material.py`、`test_build_new_material.py`、`test_query_pricebook.py` **全绿才可交付**（离线、不联网、不写数据）。
5. **能力 1 不需要快照**（v1.9.0 起）。快照只在**能力 2 / 3** 用，缺失不影响能力 1。

## 数据源策略

### 能力 1：连接器实时查（唯一主路径，v1.9.0 起）

- 一律**实时**查 `ProductObj` 与 `PriceBookProductObj`，结果即系统真身，**不存在快照滞后问题**。
- 不再需要「先快照、快照未命中再兜底」的两段式——那段逻辑随快照一起弃用。
- 通道不可用时（CLI 调用报错 / `get-current-user` 失败）→ **停止**，不要退回去读快照猜，先跑一次实查确认再问用户。
  ⚠️ **不要凭记忆判定通道状态**——失效的是 **fs-server 那条渠道**（代理网关 / SSE 直连 / API 写三路返回 HTTP 400），
  而 sharecrm 连接器 / CLI 是**可用**的（2026-10-13 实测 `query-by-fields` / `describe get` 均正常）。
- 省 token 的两条：`select_fields` 只取真正要用的列；输出走 `fmt_plan()` 的精简文本。判「有没有」必须看 `returnedCount`/`totalNumber`，**不得截断**。

### 能力 2 / 3：仍用本地底表（金蝶物料表 + 产品快照）

本地底表快、全、离线、结果可复现，是能力 2/3 的主数据源。匹配顺序：物料名称 → 规格型号 → 型号标题。
底表缺失的处理见「降级与停止」。

## 降级与停止

| 状况 | 处理 |
|---|---|
| openpyxl 缺失 | needs_setup，按 setup-guide 安装后重检 |
| 连接器 / CLI 不可用（能力 1） | 停止，说明「实时查不了的不能靠猜」，等用户恢复后再跑 |
| 源表组织无法识别 | 停止，问用户 |
| 组织不在「组织→价目表」映射表 | 停止，报组织名问用户 |
| 系统里找不到对应价目表 | 停止，报价目表名问用户 |
| 源表缺必填价格列 | 停止，列出缺失行问用户 |
| 表头语义识别失败（前 8 行找不到型号类或价格类列） | 停止，打印前 8 行原文问用户，不猜列 |
| 产品在系统查不到（能力 1） | 该行标「产品未同步」，**回报用户去金蝶建**，其余行照常；绝不自行 create |
| select_one label 转不出码值 | 原样提交并在核对清单标注（可能被拒），不静默丢字段 |
| 产品快照与明细快照均找不到（能力 2/3） | partial：不做匹配与查重，全部行进新建文件且产品列填源表原名，文件名追加「未校验」，核对清单显著标注「未经产品匹配与查重，导入前需人工核对」 |
| 金蝶物料表缺失（有产品快照，能力 2） | 降级：只按产品快照匹配，销客产品编码取自快照「唯一性ID」、物料编码取自快照「物料编号」，结果「降级说明」写明并要求人工复核 |
| 金蝶物料表与产品快照都没有（能力 2/3） | 停止，说明「无底表不做无依据匹配」，让用户先导出底表 |
