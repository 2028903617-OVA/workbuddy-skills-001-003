# 能力 1：价目表明细维护（实时查 → 确认 → 直写）

> **v1.9.0 改版（2026-10-13 用户明确）**：**不再用快照**，改为**经连接器实时查**系统已有产品与该组织启用价目表里的明细；
> 先报「哪些要新建 / 哪些要更新」→ **用户确认后**再整理价格·品牌·品类·品项并**直写落地**。
> 旧「读两份 xlsx 快照 → 生成 12/8 列导入文件 → 人工导入」路径**降级为可选**（用户明确要文件时才用）。旧文见本文件末尾「附：旧快照通道」。

## 何时用

用户给出 1 份价目表源表 xlsx，并说「加进价目表」「价目表明细导入」「处理价目表」「维护一下价目表」等。源表通常是某组织的新增产品申请表（含产品型号与 4 个价格）。

源表里若出现**我方系统里不存在的新型号**，先走能力 3 生成我方物料名，再回到本流程。若源表用的是**对方的物料名/型号标题**，先走能力 2 匹配。

## 主流程（四步，先查后写）

一条命令跑两阶段；**阶段 1 默认只读**，**阶段 2 加 `--apply`**：

```bash
python scripts/query_pricebook.py --source <源表.xlsx> --org <组织>          # 阶段 1：查
python scripts/query_pricebook.py --source <源表.xlsx> --org <组织> --apply  # 阶段 2：写（用户确认后）
```

| 步 | 做什么 | 细节 |
|---|---|---|
| ① **查产品** | 按源表型号/名称实时搜 `ProductObj` | 原名与型号各查一次；候选必须过**两闸**（型号码边界 + 品牌一致）；多条候选取与源表长度最接近的 |
| ② **查明细** | `product_id` + `pricebook_id` **双条件**查 `PriceBookProductObj` | 命中 → 【更新】；未命中 → 【新建】；结果**不得截断** |
| ③ **报用户** | 逐行输出：产品已存在/未同步、明细已有/未建、动作、待写值、品牌·大类·品项 | 精简文本省 token；要点必须齐 |
| ④ **确认后写** | 用户明确确认 → 转码值 → 构报文 → `create`/`update` | 不加 `--apply` 绝不写 |

### 关键环节说明

1. **组织（org）识别**：优先用户明示（`--org`，兼容旧参 `--brand`）；识别失败**必须问用户，不猜**。
   ⚠️ **组织 ≠ 品牌**：组织只决定「价目表」列；品牌是产品实际品牌，逐行从型号推断。
   组织 → 价目表映射见 `brand-pricebooks.md`；组织不在映射表 → **停止**，报组织名问用户。
2. **产品匹配两道闸**（`find_product()`）：
   - **品牌一致性**：源表型号与候选名都能推出品牌且不同 → 拒绝。
   - **型号码边界**：候选名的型号码必须在源表型号中整体出现，且两侧不是 `- / +`、罗马数字后缀等中断符；
     括号变体（如 `(HE)`）必须两边都有，否则是**不同产品**（实战：`F60-33Q7Pro(HE)` ≠ `F60-33Q7Pro`，物料号 .099 vs .079）。
   - 套装/变体不得跨边界命中：`洗干套装TG10TMC3+TH10HC3` 不许命中套装内单机 `TG10TMC3`。
3. **查不到产品 = 回报用户**：标「产品未同步」+ 提示「先在金蝶新建并同步，绝不自行建产品」。**该行不写**，其余行照常。
4. **品牌取值（三级兜底，2026-10-14 修订）**：① **系统产品「分类」路径首段**（去 `K-` / `K_` 前缀；段内含已知品牌词则取品牌词本身——实测 `K-东芝坐便器` → 东芝、`K_大金` → 大金）→ ② 产品名称 / 型号匹配 `BRAND_KEYWORDS` → ③ 源表品牌列**仅兜底**。冲突时以 ①/② 为准并在核对清单记一行。
5. **大类/品项**：走 `build_import.classify(model, org, src_pclass, src_pitem)` 的组织规则——乾鑫读源表（源表没有则按关键词推）、大金固定「空调/空调」、欣暖家留空、西门子交叉填法、其余走通用关键词表。
6. **select_one 转码**：`field_yy0j1__c`（产品大类）、`product_item__c`（产品品项）必须传**码值**；
   脚本 `to_code()` 自动查 describe，并缓存到 `scripts/.cache/select_one_codes.json`。label 查不到 → 原样提交 + 核对清单标注（可能被拒）。
7. **写入**：`pricebook_sellingprice` 是**默认值表达式**，API 不自动算，**必须显式传**；`discount` 是普通默认值（100）会自动带出。
   新建报文另加 `pricebook_id` / `product_id` / `record_type=default__c`。详见 `openapi-direct-write.md`。
8. **写完必做**：回读系统核对（价 / 品牌 / 大类 / 品项）→ 补《变更台账》→ 记当日日志。

## 固定规则（不可变）

- 折扣（%）恒填 100（= `discount`，普通默认值，API 自动带出 100.00%）。
- **「业务类型（必填）」= API 字段 `record_type`**，label 就叫「业务类型」，该对象只有唯一选项 `预设业务类型`（值 `default__c`）→ 直写时恒传 `record_type=default__c`。
  （导入文件通道里它是一列「业务类型（必填）」；两种叫法是同一条规则。）
- 价目表（必填）按**组织**从 `brand-pricebooks.md` 启用清单取；组织不在清单 → 停止问用户。
- **产品（必填）填系统产品名称**，**不填源表原名**（源表常少品类词或大小写不同，如 `美的热水器JSLQ27-S2-AK8 PRO` → `美的燃气热水器JSLQ27-S2-AK8 Pro`）。
- 启欣：4 个价格列与产品品项留空，其余照填。
- 产品等级：仅源表备注列出现 A–F 单字母时填「X类」，否则留空。
- 不修改源表；不擅自增删行、不改型号与价格数字、不改品牌名。
- **产品主数据不得自行新建**：系统里查不到（含「金蝶未同步」）→ **回报用户**，绝不自行 create `ProductObj`（否则与金蝶同步重复建出产品）。
- **写入必须用户二次确认**（铁律 1）；未确认只跑阶段 1。

## 已知 CLI 坑（全部实测，脚本里已封堵）

| # | 坑 | 症状 | 封堵 |
|---|---|---|---|
| 1 | **`recordResult` 两种结构** | 有命中是 **list**；无命中是 **dict** `{totalNumber, records:[], searchTemplateQuery}`（伴 `EMPTY_RESULT`）。直接 `hits[0]` 抛 **`KeyError: 0`** | `cli_query()` 统一归一化成 list |
| 2 | ★★ **`limit` 上限 50** | limit=51/100/200 时服务端 notice **`LIMIT_EXCEEDED`**（`status=NOT_EXECUTED`，**查询根本没跑**），`recordResult` 退化成 `{totalNumber:0, records:[]}` —— **不报错、静默 0 条**。会被误读成「记录不存在」→ **重复建明细** | ① 自动夹到 `MAX_LIMIT=50`；② notices 出现阻断码 → **抛 `CliError`**，绝不返回空；③ >50 条用 `cli_query_all()` 翻页 |
| 3 | **偶发 `fetch failed`** | 同一条命令第 2 次就成功；不重试会误判成「对象/记录不存在」 | `_run_cli()` 自动重试 4 次、线性退避 |
| 4 | **`fuzzy_ok()` 返回元组** | `(ok, reason)` **恒为真值**，写成 `if fuzzy_ok(...)` 会让两道闸**完全失效** | 必须取 `[0]` |
| 5 | ★ **品牌闸词表不全** | `bi.brand_words()` 用 `BRAND_WORDS`（仅 31 词），是 `BRAND_KEYWORDS` 的**子集**。未收录品牌（林内/樱花/大松…）返回空集 → 判据 `if bs and bc and not (bs&bc)` 跳过 → **不同品牌静默放行** | 叠加 `_brand_gate()`（走全量 `BRAND_KEYWORDS`）：两侧都识别得出品牌且不同 → 拒 |
| 6 | **整串 `like` 命中不了** | 源表写完整名称（`美的电热水器JSQ27-M12 MAX`），系统名是另一套品类词+大小写（`美的燃气热水器JSQ27-M12 Max`）→ 整串查不到 → 误判「金蝶未同步」 | `find_product()` 逐级放宽候选：完整串 → **型号码 token**（`bi.model_tokens`）→ 再两道闸把关 |
| 7 | **`operator` 必须小写** | `eq / n / like / in / gt / gte / lt / lte / between`；写 `EQ`/`GE` 报 `INVALID_ARGUMENT` | 脚本内固定小写 |
| 8 | **返回字段名是中文 label** | 实测 `价目表售价` / `销售结算价` / `成本价` / `品牌负责人审核价` / `品牌` / `价目表明细编号` / `产品名称` / `价目表名称`；`_id` 原样 | 取值 label 与 apiName 都试 |
| 9 | ★ **分类首段不总是纯品牌** | 产品「分类」首段可能带品类词，实测 `K-东芝坐便器`（若直接取首段 → 品牌写成「东芝坐便器」，错） | 去 `K-`/`K_` 前缀后**再过一遍 `BRAND_KEYWORDS`**，命中则取品牌词本身 |

> `--raw` 可拿原始码值（人员/部门/引用字段默认返回显示名，伴 `DISPLAY_VALUE_APPLIED`）；本流程不依赖这些，无需加 `--raw`。
> **消息面点名**：`LIMIT_EXCEEDED` 的服务端原话还提示「下一页 offset 才应为当前 offset 加 applied limit，不要重复使用同一个 offset」→ 翻页必须按实际 applied limit 递增。

## 降低风险的实战要点

- **先查后报、再写**：把「新建 X 行 / 更新 Y 行 / 产品未同步 Z 行」先摆给用户，等确认。一次跑批通常几十行，误写的代价远高于多问一句。
- **同产品去重**：若同一系统产品被源表**多行**命中，精确同名行优先保留，其余行降级进核对清单（「模糊撞名·已降级」）；多行精确同名时同价去重、异价记「同名多行异价·待确认」。防止同一产品建出两条明细。
- **产品冲突记清单**：品牌冲突、分类未匹配、label 转码失败，全部落清单，不静默。

## 质量自查清单

- [ ] 阶段 1 先跑，结果已报用户；**未确认没有写**
- [ ] 每个写入行的产品名来自系统命中值（不是源表原名）
- [ ] 产品未同步行**未写入**，且已提示用户去金蝶建
- [ ] `pricebook_sellingprice` 显式传值；`record_type=default__c`
- [ ] 折扣 100、业务类型「预设业务类型」全覆盖无遗漏
- [ ] 启欣行价格与品项为空
- [ ] 金额纯数字、无文本、无千分位逗号
- [ ] 大类/品项已转码值；转不出的已标注
- [ ] 写完**已回读核对**系统真身（价 / 品牌 / 大类 / 品项）
- [ ] 《变更台账》已补、`verify` 通过
- [ ] 全流程**未新建任何产品**

## 附：旧快照通道（v1.9.0 起降级为可选）

> **仅当用户明确要「导入文件」时启用。** 新流程请用上面的 `query_pricebook.py`。

旧路径 = `scripts/build_import.py`：读产品主数据快照 + 明细快照，匹配 + 查重，输出三份文件：

- `{组织}_新建价目表明细_{YYYYMMDD}.xlsx` — 12 列
- `{组织}_更新价目表明细_{YYYYMMDD}.xlsx` — 8 列（无重复行不生成）
- `{组织}_产品核对清单_{YYYYMMDD}.xlsx` — 待同步 / 重复 / 分类未匹配（无警示项不生成）

**为什么降级**：快照滞后 1–3 天是常态（金蝶当天新建的产品快照必然查不到），历史上多次把「滞后」误判成「金蝶未同步」；
且「生成文件 → 人工导入」多一道人工环节。实时查 + 直写消除这两点。

**若仍需旧路径**，两条已知缺陷必须靠连接器复核补救：

| 失败类型 | 真实例子 | 后果 |
|---|---|---|
| **错配**（子串/型号包含截短） | 源表 `美的电热水器F60-33Q7Pro(HE)` 命中快照里不带 `(HE)` 的 `F60-33Q7Pro`（另一个产品，物料号 .099 vs .079） | 导入到错误产品，价格挂错 |
| **漏配**（三种策略全落空） | 源表 `美的净饮机JR2288T-RO` vs 系统名 `美的台式净饮机JR2288T-RO冰川银` | 被判「金蝶未同步」，白白漏掉 |
| **同型号不同产品** | `GMV-NHDR63PS/Fb1` 与 `…/Fb` 是两种机型 | 挂错型号 |

旧路径自查补充：新建文件「产品（必填）」列无重复；核对清单含**快照日期**与「快照之后的新增未覆盖」说明。
