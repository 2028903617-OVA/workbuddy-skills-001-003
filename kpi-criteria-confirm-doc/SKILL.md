# 考核口径确认表 生成技能

> 适用：当老板/管理层要对「绩效、提成、考核指标的统计口径」做书面确认（签字留痕）时使用。
> 产出：一份 A4（默认横向）docx，可打印，含版本对比、差异一览、签字/意见栏。
> 沉淀来源：欣暖家 2026-07 月度绩效奖金 4 项考核口径（①第一成交率金额 ②录入ABC线索数量 ③成交ABC顾客数 ④月度整体销售），多轮老板意见迭代。

---

## 一、何时使用本技能

- 用户说「跟老板确认考核口径」「出一份口径确认表签字」「统计口径要确认一下」。
- 任务可能是 **多口径对比**（现方案 vs 拟调整方案，需勾选采用哪个）→ 用 A/B/C 版本结构。
- 任务也可能是 **直接确认单一口径**（没有备选方案，只要老板签字认可）→ 用单版本结构（只放「现方案」即可，去掉 B/C）。
- 只要有「考核项 + 统计口径 + 示例 + 签字确认」这类需求，就加载本技能。

---

## 二、两种交付结构（按任务选）

### A. 多口径对比确认（有 A/B/C 版本）
用于老板在多个口径里选一个。文档骨架：
1. **标题** + 副标题（版本说明：`A版=现方案 | B版=拟调整1 | C版=拟调整2`）
2. **重要声明**（判定前提，如回款审批通过才计入）
3. **通用基础规则**（A/B/C 都适用的：金额依据、时间依据、回款状态、奖金标准、周期维度）
4. **判定逻辑小节**（如「第一成交判定」，多版本通用）
5. **各版本方案**：A版（现方案，蓝色）、B版（拟调整1，橙色）、C版（拟调整2，绿色），每个版本内用「考核项 / 统计口径 / 示例」三列表
6. **差异一览表**（横向对比 A/B/C 在每项上的口径差异 + 对奖金影响）
7. **确认签字**：每行「考核项 + 采用方案(□A □B □C) + 签字」+ 意见栏 + 确认人/日期

### B. 直接确认单一口径
没有备选 → 去掉 B/C 与差异一览表，第 5 节只放「现方案」，第 7 节签字栏的「采用方案」列改为「是否确认 □是 □否」或直接删列。其余结构不变。

> 实战经验：欣暖家最终交付是 **A=现方案 + B/C=拟调整**，且 ③成交ABC顾客数 在 A/B/C 三版口径不同（这是最核心的对比点）。

## 三、内容编排铁律（来自「做事要严谨」准则）

交付前必须逐项自检，错误一次都不能再犯：

1. **命名统一**：同一概念全文档只用一个词。欣暖家案例里「第一成交」不得写成「首成 / 首次成交」。用户改名后全量替换并复核。
2. **不要把 A 指标的逻辑误套到 B 指标**：曾把①「仅第一成交」误写到③，导致③定义与示例自相矛盾。每个考核项的定义/示例/判定条件要**各自独立核对**。
3. **用户精确定义即权威**：用户给的示例（如「5/5 第一成交进①、5/22 再成交进③、同客户同月判重不进③」）必须逐字还原，不得走样。
4. **长文档全局一致性扫描**：写完用 grep 扫残留词（旧命名、被要求删除的字眼、A/B/C 级客户等），确认无遗漏。
5. **示例数据自洽**：表内示例数字必须与所写规则自洽（如「净新建 8 条」要对应「新建10−第一成交2」）。

## 三·B、交付后回读复核（每次做完文件必做 · 最高优先级）

> 来源：用户 2026-08-06 硬性要求。不要只凭"我记得写了什么"就交付——**生成/写出文件后必须回读真实产出再 present**。

1. **回读实际内容**：docx 用文本 dump（或打开校验）读真实段落/表格；代码/配置直接 Read 文件。逐项核对，不靠记忆。
2. **查内容 vs 实际业务逻辑冲突**：口径、公式、判定条件、示例数字是否自洽、是否违背系统真实字段/规则（如金额按订单对象、回款审批通过才计入等前提）。发现冲突立即改。
3. **查要求 vs 前面对话内容不一致**：拿成品与**本轮及历史对话里用户已确认的需求/示例/改名/删除项**逐条比对——有没有漏掉用户手改的文字、有没有把已删除措辞又写回、有没有和之前确认的口径自相矛盾。
4. 这两项复核是硬动作，不是建议；宁可多花一步回读，也不让用户抓出"和前面说的不一样 / 逻辑对不上"。

## 四、docx 生成技术（Node `docx` 库）

### 环境
- 库：`docx` v9.6.1（已装在 `C:/Users/Administrator/.workbuddy/binaries/node/workspace/node_modules`）。
- 运行方式（必须设 NODE_PATH，否则 require 找不到）：
  ```
  NODE_PATH=C:/Users/Administrator/.workbuddy/binaries/node/workspace/node_modules C:/Users/Administrator/.workbuddy/binaries/node/versions/22.12.0/node.exe scripts/gen_template.js
  ```
- 字体统一用 `Microsoft YaHei`。

### 布局要点（紧凑、可打印、小节不跨页）
- **页面**：A4 横向（`size: { width: 16838, height: 11906 }`, `PageOrientation.LANDSCAPE`），页边距 `600`（约 0.42cm，别用默认 1440）。
- **小节不跨页**：表格每行 `TableRow({ cantSplit: true })`——这是 docx 9.6.1 唯一可靠防跨页手段。
- **⚠️ keepWithNext 不会被序列化**：`Paragraph({ keepWithNext: true })` 在 docx 9.6.1 里属性被忽略，**不要依赖它**。要靠 `pageBreakBefore: true` 在「大分组前」强制分页来实现「一页放多节、小节内容不跨页」。
- **紧凑分页策略**（3 页示例）：用 **2 个分组分页符**（如「三版前」「五版前」）把内容切成 3 组，其余靠自然流向排版，比「每节一页」松但比「全塞一页」清晰。间距：`heading` before 160 / after 80，`para` after 60，声明/签字前可加大到 160。
- **版本配色**（一眼区分）：A版=`1F4E79`(蓝) / B版=`C55A11`(橙) / C版=`548235`(绿)；标题=`1F3864`；声明红框=`C00000`；表头灰=`F2F2F2`。

### 可复用骨架
`scripts/gen_template.js` 已封装好：`run() / para() / heading() / subtitle() / cell() / table()` 六个 helper，含颜色常量、页面设置、签名栏模板。**每次只需改 `children.push(...)` 的内容区**，不要重写 helper。

## 五、校验与交付

### 结构校验
用 docx 技能自带的 `validate.py`（需 lxml / python）：
```
python <docx skill>/scripts/office/validate.py <输出文件>.docx
```
看到 `PASSED` 再交付。主要防 XML 结构错误导致 Office 打不开。

### ⚠️ 腾讯文档预览锁（EBUSY）
若文件已在腾讯文档预览中打开，**覆盖写会失败（EBUSY）**。处理：
- 改一个新文件名生成（如 `_v2`、`_紧凑版`），不要反复重试同名。
- 提示用户关掉预览后再做文件归并/覆盖。
- 旧临时文件（草稿版）若被锁删不掉，等用户关预览后清理，不要硬删。

## 六、欣暖家字段事实（参考范例，非通用）

> 这是本技能的「实战弹药库」，新项目可替换为对应系统的字段。详见 `references/field_facts.md`。

- 4 项考核：①第一成交率金额 ②录入ABC线索数量 ③成交ABC顾客数 ④月度整体销售；每项达标 300 元/月，合计上限 1200 元/月。
- 反写对象 `object_oEmfu__c`（月度绩效），4 个奖金字段 `first_deal_bonus__c` / `abc_count_bonus__c` / `abc_conversion_bonus__c` / `target_achieve_bonus__c`，合计 `total_assessment_bonus__c`（公式，不可写）。
- **金额按订单对象** `SalesOrderObj` 统计（不从回款明细汇总）；**时间按回款日期**；**回款审批通过（`life_status='已回款'`）才计入**。
- **第一成交判定**：首次回款日期 ≤ 线索创建日期 且 已回款。
- **③ 三版去重口径**：A=客户信息去重（第一成交/ABC 不重复计数，每客户仅 1 次）；B=客户+回款日联合去重（同回款日 1 个、不同各 1 个，靠新增文本字段承载）；C=客户信息当月去重（同客户本月 1 个，含第一成交则各计 1 个，系统现有「客户姓名唯一计数」即可）。
- 匹配键：人员 `person_name__c` + 年 `year__c` + 月 `month__c` + 品牌 `brand_name__c`（欣暖家=`6p1Rxc395`）。

## 七、执行步骤（标准流程）

1. 问清任务类型：多口径对比 / 直接确认？需要确认哪些考核项？现方案口径是什么？有无拟调整方案？
2. 按第二节选结构，套用 `gen_template.js` 骨架填内容。
3. 内容区严格按第三节铁律自检（命名、不误套、示例自洽、grep 残留）。
4. `NODE_PATH=... node gen_template.js` 生成 docx → `validate.py` 校验。
5. 遇 EBUSY 换名；**交付前按「三·B 交付后回读复核」回读真实文件**：查内容 vs 实际逻辑冲突、查要求 vs 前面对话不一致，确认无矛盾再 present。
6. present 给用户，询问是否需要清理旧草稿。
