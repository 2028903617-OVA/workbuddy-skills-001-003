# 自主服务预约

## 1. 适用场景

### 1.1 适用场景

当客户表达以下诉求时，使用本技能：

- 预约上门服务
- 预约远程支持
- 预约设备检修
- 预约安装、调试、巡检、回访等服务

### 1.2 不适用场景

以下情况不要使用本技能：

- 客户在咨询知识类问题
- 客户在查询服务处理进度
- 客户明确要求人工客服

## 2. 执行路径


**第一步：判断是否在发起服务预约**

分析客户输入，判断是否属于预约上门、远程支持、设备检修等场景。

🔴 CHECKPOINT：如果客户不在发起服务预约（属于知识问答、进度查询等），终止执行并转交对应技能。

**第二步：逐步收集必要信息**

创建服务请求前，必须逐步收集以下 5 项信息。每收集一项确认一项，禁止一次性要求客户填写完整长表单，已收集的信息不要重复询问。

1. 主题（`subject`）：根据上下文总结为一句服务预约主题
2. 问题描述（`problem_desc`）：描述客户的预约事项和问题情况
3. 服务地址（`service_address`）：客户提供的明确地址
4. 期望服务时间（`appointment_processing_time`）：客户期望的服务时间
5. 联系电话（`contact_tel`）：可联系的联系电话


- `record_type`：默认传 `default__c`
- `owner`：默认传当前用户 ID 数组格式


**第三步：整理 subject 和 problem_desc**

根据已收集的上下文，整理为准确的 subject 和 problem_desc 字段值。

🔴 CHECKPOINT：创建前检查 5 项必要信息是否全部收集完毕。缺任何一项不得执行创建，必须继续补充。

**第四步：直接创建服务请求对象**

信息完整后，使用以下命令直接创建：

```bash
sharecrm data record create --data '{"object_api_name":"ServiceRequestObj","object_data":{"subject":"<主题>","problem_desc":"<问题描述>","service_address":"<服务地址>","appointment_processing_time":"<期望服务时间>","contact_tel":"<电话>","record_type":"default__c","owner":["<当前用户ID>"]}}'
```

创建成功后告知客户已登记，无需二次确认。

**第五步：处理紧急情况**

如果客户表达以下情况：

- 停机
- 影响生产
- 无法启动
- 需要尽快上门

则继续收集必要信息，并在回复中体现紧急处理语气。

推荐表达：

- 我理解您这边情况比较紧急，我先帮您登记服务请求并优先整理预约信息。

## 3. 禁止行为

- 禁止一次性让客户填写完整长表单
- 禁止重复询问已提供的信息
- 禁止在预约场景下强行转回知识问答
- 禁止在信息不足时直接假设并创建预约
- 禁止用内部术语向客户描述流程
- 禁止创建成功后要求客户二次确认

## 4. 输出结果

### 4.1 成功输出

```
好的，我已为您整理好服务预约信息，正在为您提交服务请求。

预约信息如下：
- 服务主题：空调维修预约
- 服务地址：北京市海淀区中关村大街 1 号
- 期望时间：2026 年 4 月 2 日上午
- 联系电话：138****5678

后续将按照预约信息继续处理。
```

### 4.2 失败输出

```
为了继续帮您预约服务，还需要补充一下联系电话。
```

**失败输出（创建失败）**

```
当前服务请求暂未提交成功，建议您稍后重试，或我可以继续协助您联系人工客服。
```

## 失败模式

| 场景 | 表现 | 处理方式 |
|------|------|----------|
| 信息收集过程中客户中断 | 客户不再回复 | 等待 30 秒后提示"是否继续预约"，如仍无回复保存已收集信息并提示可稍后继续 |
| 客户拒绝提供某项信息 | 明确表示不想提供 | 礼貌说明该信息为必填项，如仍拒绝则终止创建并建议联系人工客服 |
| 联系电话格式无效 | 号码位数不对或包含非法字符 | 要求客户重新提供正确的联系电话格式 |
| 服务地址不完整 | 缺少关键地址信息 | 追问缺少的地址要素（街道/门牌号等） |
| create 命令返回错误 | 接口返回错误码 | 提示客户稍后重试，或联系人工客服协助处理 |
| 客户在预约场景中途转咨询知识类问题 | 话题切换 | 先完成预约信息收集，再判断是否需要转交知识库问答技能 |

## 验证清单

### 测试用例

**测试用例 1：正常服务预约**

**用户输入**：我要预约明天上门修空调

**预期行为**：
1. 判断为服务预约场景
2. 逐步收集 5 项必要信息（地址、电话等）
3. 整理 subject="空调维修预约"，problem_desc="客户反馈空调故障，需要明天上门检修"
4. 必要信息完整后执行 create 命令
5. 告知客户已登记服务预约

**测试用例 2：非预约场景拦截**

**用户输入**：空调不制冷怎么办

**预期行为**：
1. 判断为用户在咨询知识类问题
2. 终止执行
3. 转交知识库问答技能处理

### 验证检查清单

- [ ] 客户输入属于服务预约场景
- [ ] 已逐步收集 5 项必要信息：subject、problem_desc、service_address、appointment_processing_time、contact_tel
- [ ] 已根据上下文准确整理 subject 和 problem_desc
- [ ] 服务地址、联系电话、期望服务时间均有效
- [ ] 创建对象为 `ServiceRequestObj`，字段统一放在 `object_data` 中
- [ ] 未使用 flat flags、describe、help 或其它未指定命令格式
- [ ] 未重复询问已提供的信息，未一次性要求客户填写完整长表单
- [ ] 紧急场景已体现紧急处理语气
