# 产业链外部资料规则

本文定义 `account-chain-analysis` 如何使用企业情报数据、官网、年报、公告、新闻和公开 web 来源补充产业链分析。内容参考原始 `sfa-industry-chain-analysis` 中的结构、链位和关系识别思路，并按当前专题 Skill 边界收敛。

## 1. 外部资料定位

外部资料用于回答四类问题：

- 客户所在业务链条的价值流向是什么。
- 客户位于产业链什么位置，扮演什么价值角色。
- 客户有哪些上游、下游、渠道、生态、集团或资本关系。
- 这些关系会对客户经营、需求、风险和相关情报信号带来什么影响。

使用原则：

- 先锚定目标客户主体，再读取外部资料。
- 内部企业情报 allowlist 优先沿用主 Skill 的 `account-due-diligence-report/references/enterprise-cli-map.md`。
- 企业情报 CLI 只能作为优先来源，不是唯一来源；CLI 不存在、字段不足、返回为空、覆盖不全或不能解释关系时，才继续使用 web search、官网、年报、公告和权威公开资料补查。
- 外部资料必须保留来源、时间口径和支撑内容。
- 外部资料只能解释客户关系，不得直接展开拓客对象、二跳扩展或销售动作。
- 没有证据时进入 `gaps`，不得编造链位、关系对象或关键依赖。

## 2. 资料域与证据要求

| 维度 | 优先资料域 | 证据要求 | 可支撑内容 |
|:---|:---|:---|:---|
| 主体与主营 | 工商基础、官网、年报、主营介绍 | 来源 + 日期/报告期 | 主营业务、业务边界、客户主体身份 |
| 链位与价值角色 | 主营介绍、产品/服务、目标客户、交付方式、行业模板 | 来源 + 链位判断依据 | 上游/中游/下游、平台/渠道/服务商/集成商定位 |
| 下游关系 | 企业情报业务信息、客户案例、招投标/中标、公告、官网案例 | 关系对象 + 时间 + 来源 | 下游客户、项目客户、服务对象 |
| 上游关系 | 官网生态/采购信息、年报、公开合作、经营范围推断 + 补证 | 推断依据 + 补证来源 | 上游环节类型、典型供应商类型、弱关系对象 |
| 渠道/生态 | 官网合作伙伴、联合方案、生态公告、新闻 | 合作对象 + 合作内容 + 时间 | 渠道合作、生态协同、平台伙伴 |
| 集团/资本 | 股东、对外投资、分支机构、融资、公告 | 对象 + 关系性质 + 时间 | 控制关系、区域覆盖、组织复杂度、采购归口 |
| 关键依赖 | 上下游/渠道/资质/平台/区域资源等关系证据 | 依赖事实 + 影响解释 | 客户依赖谁、为什么形成依赖、依赖影响 |

## 3. 证据优先级

产业链专题涉及关系判断时，证据优先级为：

1. CRM 原值和内部客户原话中与客户链路直接相关的业务片段。
2. 企业情报结构化数据：工商、股东、对外投资、分支、融资、主营业务、公开客户。
3. 官网、年报、交易所公告、监管公开信息。
4. 招投标、采购、中标和项目公告原文。
5. 权威新闻、权威行业资料、公开合作报道。
6. 行业模板和公开业务规律推断。

规则：

- 1-4 级可以直接支撑正式判断。
- 5 级可以支撑中强度判断，最好与 2-4 级交叉验证。
- 6 级只能标 `inferred`，不能单独支撑强结论。

## 4. 关系识别规则

### 4.1 下游关系

- 公开客户、项目客户、服务对象可以作为下游关系证据。
- 由招投标或项目公告反推的客户关系，只能说明“发生过项目或采购关系”，不能自动写成长期稳定客户。
- 公告未明确金额、频次、期限时，不夸大关系强度。

### 4.2 上游关系

- 没有直接供应商数据时，优先输出上游环节类型，例如算力、原材料、设备、集成服务、渠道资源。
- 只有在官网、公告、案例或权威报道出现明确合作方时，才输出具体上游对象。
- 仅凭经营范围和行业常识推理出的上游对象，一律标 `inferred`。

### 4.3 渠道与生态

- 必须区分客户卖给谁、通过谁卖、和谁协同。
- 联合解决方案、生态伙伴、开放平台、技术联盟等可作为生态关系。
- 经销、分销、代理、区域合作等可作为渠道关系。
- 不把合作伙伴、渠道商和终端客户混为一类。

### 4.4 集团/资本

- 股东、分支、对外投资、融资和同资方关系可以用于解释控制、组织复杂度、采购归口和区域覆盖。
- 集团/资本关系不能自动当成上下游关系。
- 只有明确资料表明存在供货、采购、渠道或项目关系时，才将集团关联对象写入其他关系类别。

## 5. 时效和覆盖范围

| 资料域 | 默认时间窗 | 使用优先级 |
|:---|:---|:---|
| 工商、股东、分支、对外投资 | 当前有效结构 + 近年变化 | 主要对象、关键变化 |
| 融资、资本事件 | 近 3-5 年 | 对链位、技术路线或扩张有影响的事件 |
| 新闻、公告、官网合作 | 近 12-24 个月 | 最近且与主营业务相关 |
| 招投标、采购、中标 | 近 12-24 个月 | 金额较大、主营相关、权威来源 |
| 年报、上市公告 | 最近 1-2 个报告期 | 优先正式披露口径 |

规则：

- 只拿到旧资料时，标注“最新可得资料为 <时间>”。
- 明显非全量时，在 `meta.retrievalCoverage` 中记录覆盖范围；正文仅在影响理解时表达。
- 列表量过大时，优先保留主要对象、近期变化和对客户判断最关键的关系。

## 5A. web search / web fetch 控制

- 主报告或本专题已有 `company conc`、招投标、新闻、上市公告等可支撑链位和关系判断时，不为补充背景泛化 web search。
- 默认最多 1-2 个精准 query，每个 query 只消费前 3-5 条高质量结果；query 应包含企业全称、产品/业务、合作对象、上下游或项目关键词。
- web fetch 只抓官网、公告、监管、交易所、招投标原文、年报和权威新闻。遇到“操作过于频繁”、访问受限、登录/验证码、403、404、加载失败、明显反爬或长时间无正文时立即降级。
- 上游/下游具体对象证据不足时，可输出环节类型或低置信推断，不为凑具体企业名长时间抓取低价值网页。

## 6. 能力降级

| 情况 | 处理 |
|:---|:---|
| 企业情报结构化数据不可用 | 转官网、年报、公告和公开 web 来源补查，对应维度降级 |
| 链位证据不足 | 只输出已确认位置或“结构信息有限”，不强下完整结论 |
| 下游关系仅来自单条招投标 | 保留为项目型关系，不升格为长期客户 |
| 上游无直接证据 | 只输出上游环节类型或低置信度推断 |
| 集团/资本资料不足 | 对应维度进入 `gaps`，不替代供应链判断 |
| 来源冲突 | 保留冲突来源和时间口径，降低判断强度 |
| CLI 返回为空、字段不足或覆盖不全 | 少量精准 web search、官网、年报、公告、招投标原文和权威新闻补查；公开来源仍无证据时再进入 `gaps` |

## 7. 禁止用法

- 不把公开资料写成 CRM 内部事实。
- 不把集团/资本关系直接翻译成供应链关系。
- 不把招投标反推客户写成稳定大客户。
- 不为了模板完整强行补上游、下游、渠道、生态四类关系。
- 不输出二跳拓展、候选池、查重、定档或销售动作。

## 8. 写入独立报告数据模型

- 主体和主营资料写入 `meta.targetCompany` 与 `crmContext.account.businessSummary`。
- 结构和链位判断写入 `chainContext.chainStructure`、`chainContext.chainPosition`、`chainContext.valueRole`。
- 上游、下游、渠道、生态、集团/资本关系写入 `chainContext.upstream`、`chainContext.downstream`、`chainContext.channels`、`chainContext.ecosystem`、`chainContext.groupCapitalRelations`。
- 关键依赖写入 `chainContext.keyDependencies`。
- 与发问方相关的客户侧链路信号写入 `sellerRelevantSignals`。
- 证据统一写入顶层 `evidence`，正文字段用 `evidenceRefs` 回链。
- 证据不足、时效过旧、来源冲突或主体不清优先写入 `chainContext.gaps`，必要时同步写入顶层 `gaps`。
