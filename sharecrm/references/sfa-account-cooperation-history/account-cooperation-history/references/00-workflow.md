# 客户合作历史分析执行流程

本文是 `account-cooperation-history` 的主流程 reference。主 `SKILL.md` 负责入口，本文件负责执行顺序、独立/编排调用两种输出模式和降级规则。

## 阶段顺序

```text
用户输入客户 / 合作历史问题
  ↓
A. 客户主体锚定
  ↓
B. 识别用户角色和场景
  ↓
C. 卖方画像读取
  ↓
D. 公开合作事件采集
  ↓
E. CRM 内部历史接触采集
  ↓
F. 合作事件去重与角色分类
  ↓
G. 供应商关系、竞品占位和业务含义映射
  ↓
H. 形成数据模型并生成结果
  ↓
I. 质量自检
```

## A. 客户主体锚定

执行要求：

1. 先确认客户主体，并抽取简称、品牌名、产品名、股票简称、城市、行业/业务关键词等主体辅助锚点。
2. 用户输入不是完整工商名称时，先按 `enterprise-cli-map.md` 调用 `sharecrm intelligence company search` 做一次结构化候选召回；候选可解释用户输入后，再进入企业批量取数，不先进入 web search。
3. 高置信候选可自动选中；多家候选都可能匹配、集团/子公司/分公司混杂或辅助锚点冲突时，返回前 3-5 个候选让用户确认。
4. 主体确认后统一使用工商全称，并用 `sharecrm intelligence company conc` 的批量结果补充业务、竞品、融资、投资和股东背景。
5. 主体未确认时，不输出完整合作历史结论。

## B. 识别用户角色和场景

执行要求：

1. 判断用户是销售、销售管理者、售前、客户成功、风控/签约还是其他角色。
2. 默认按销售视角输出。
3. 角色只影响表达重点，不改变事实口径。

## C. 卖方画像读取

目标是让合作历史分析具备发问方语境，但不把卖方画像展示在结果中。

执行要求：

1. 优先按 `business-context.md` 中的已验证配置 CLI 读取 `service_models`。
2. 配置不足时，按 `business-context.md` 使用用户明确上下文、CRM 产品/服务对象摘要、近 12-24 个月成交摘要降级。
3. 卖方画像缺失时仍可输出合作事实，但不做强相关性判断。

## D. 公开合作事件采集

公开合作事件包括：

- 招投标、采购、中标和项目参与
- 战略合作和签约新闻
- 官网合作案例
- 上市公司重大合同或合作公告
- 供应商合作、客户合作和公开生态合作

执行要求：

1. 公开合作采集前必须读取 `enterprise-cli-map.md`；主报告已取得的招投标、新闻、上市公告和公开动态结果可复用，字段不足时再按本专题 CLI map 补查。
2. 合作历史采集优先顺序：CRM 内部合作记录 -> `market bidding-pinganzhengxin` 的 `companybidmaininfo` -> `market bidding-pinganzhengxin` 的 `companybidentityinfo` -> `market get-news` -> 必要时 `market search-mentions` -> 最后才 web search / 官网 / 公告原文。
3. 招投标、采购、中标事件并入合作历史主链路。
4. 每条事件都要保留来源和时间口径。
5. 内部 `company / market / listed` CLI 已覆盖的数据域，不先 web search；CLI 不可用、返回空、字段不足、角色解释不清或需要权威公开原文补证时，才少量使用 web search / web fetch。
6. 公开来源的优先级、时效、去重和降级规则按 `external-sources.md` 执行。

## E. CRM 内部历史接触采集

内部记录包括：

- 联系人覆盖
- 历史商机
- 合同与订单
- 销售记录
- 历史失败记录

执行要求：

1. 只输出业务相关摘要。
2. 不暴露对象 API 名和内部记录 ID。
3. CRM 不可用或无数据时，明确标注信息不足。
4. 查询顺序、对象选择和写入规则按 `crm-context.md` 执行。

## F. 合作事件去重与角色分类

执行要求：

1. 对同一项目、同一合作或同一合作对象的重复记录做归并。
2. 区分采购方 / 中标方 / 参与方。
3. 区分客户方、供应商、生态伙伴、项目方、集团/关联方、竞品/替代供应商和内部关系对象。
4. 供应商或竞品类型不清时，进入待核实。

## G. 供应商关系、竞品占位和业务含义映射

执行要求：

1. 解释合作类型、合作强度和业务领域分布。
2. 解释供应商集中度、合作偏好和竞品占位。
3. 解释对客户经营、需求、风险和相关情报信号的影响。
4. 只输出客户侧信号，不输出销售执行动作。

## H. 形成数据模型并生成结果

### 独立调用模式

1. 先按 `references/schemas/standalone-report-data-model.md` 形成 `meta / crmContext / cooperationContext / cooperationHistory / sellerRelevantSignals / gaps / evidence`。
2. 再按 `output-contract.md` 输出完整合作历史分析结果，包括：

- 合作历史情报结论
- 合作时间线
- 合作对象分类分析
- 合作业务领域分布
- 供应商关系与合作偏好
- CRM 内部历史接触摘要
- 机会信号与壁垒信号
- 待核实事项
- 证据来源

### 编排调用模式

编排调用模式仍必须先完成本 workflow 的关键步骤；不得只读取 `SKILL.md` 后基于上游主报告数据直接生成结论。至少读取 `enterprise-cli-map.md`、`output-contract.md`、`schemas/insight-data-model.md`、`cooperation-types.md`、`bidding-merge-rules.md`、`external-sources.md` 和 `crm-context.md`。无法完整执行时，在结构化结果中写明降级原因。

按 `references/schemas/insight-data-model.md` 返回以下结构化结果：

- 合作对象
- 合作类型
- 合作内容
- 业务领域
- 关系强度
- 供应商 / 竞品 / 项目合作摘要
- 内部历史接触摘要
- 对客户经营、需求、风险和相关信号的影响
- 关键证据
- 待核实事项

独立调用和编排调用必须消费同一组事实与证据，不得出现口径漂移。

## I. 降级规则

| 情况 | 处理 |
|:---|:---|
| 客户主体多候选 | 中止，要求用户确认 |
| 客户主体未完全确认 | 允许输出部分合作判断，但必须标注主体待确认 |
| 公开合作事件不足 | 输出已确认事件，并标注“公开合作证据有限” |
| CRM 内部记录不足 | 不编造内部接触结论，只说明信息不足 |
| 供应商 / 竞品类型不清 | 进入待核实，不强下结论 |
| 卖方画像缺失 | 输出客户事实，不做强相关性判断 |
