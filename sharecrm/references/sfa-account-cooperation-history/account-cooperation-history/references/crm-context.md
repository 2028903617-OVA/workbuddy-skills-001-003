# CRM 内部上下文规则

本文定义 `account-cooperation-history` 如何使用 CRM 内部记录补充合作历史分析。

## 1. 使用范围

CRM 内部记录主要用于：

- 锚定客户主体和内部客户身份。
- 判断是否已有历史接触、历史商机、合同、订单、回款或失败记录。
- 补充联系人覆盖、项目推进、履约背景和内部合作深度。
- 为公开合作事实提供内部业务上下文，但不替代公开证据。

## 2. 查询原则

1. 先识别对象，再读取对象描述，再决定查询内容。
2. 默认从预设对象开始，不做自定义对象全量扫描。
3. 只有字段 label、类型、选项和关联关系能支撑合作历史解释时，才纳入查询。
4. 输出正文只解释业务含义，不展示对象 API 名、字段 API 名、SQL 或内部记录 ID。

## 3. 默认读取顺序

### 3.1 客户对象

目标是确认 CRM 中是否已有该客户，以及客户档案能否提供合作背景。

优先关注：

- 客户分层、客户状态、区域、集团归属、当前负责人。
- 业务线、项目阶段、合作状态等能帮助理解合作背景的字段。

### 3.2 联系人和活动

用于判断：

- 是否已有关键联系人覆盖。
- 是否存在历史拜访、会议、方案交流、失败原因或长期停滞记录。
- 是否能从活动摘要中提炼项目型合作、生态合作、供应商竞争或采购习惯线索。

### 3.3 商机、合同、订单、回款

用于判断：

- 我方是否与客户发生过正式合作或推进到较深阶段。
- 合作属于项目、产品、服务、框架协议还是阶段性接触。
- 是否存在履约、续费、回款或中途失败等背景。

如果只能说明“内部曾接触”，但不足以解释合作深度或关系性质，则只保留摘要，不强下结论。

## 4. 可选关联对象

只有以下情况才探索关联对象或自定义对象：

- 用户明确提到某类内部合作对象。
- 预设对象不足以解释合作历史、历史失败或履约背景。
- 对象描述显示存在明显相关的关联对象，且字段含义清晰。

探索时仍必须先读对象描述，再决定是否查询。

## 5. 写入规则

- 客户业务摘要写入 `crmContext.account.businessSummary`。
- 联系人、活动、商机、合同、订单、回款等内部记录，优先按主报告口径写入 `crmContext.contacts`、`activities`、`opportunities`、`contracts`、`orders`、`payments` 的业务摘要。
- 与合作专题直接相关的内部记录，再提炼写入 `cooperationContext.internalHistory`。
- 能解释供应商关系、项目偏好、替换难度、合作窗口或风险的内部线索，可同步写入 `cooperationContext.businessImplications`。
- 与发问方业务相关的客户侧合作信号，可同步写入 `sellerRelevantSignals`。

## 6. 能力降级

| 情况 | 处理 |
|:---|:---|
| `describe` 不可用 | 标 `crmContext.objectDescribeDriven=false`，仅保留已确认内部摘要 |
| 客户名称无命中 | 标“客户未在 CRM 命中”，不伪装为已有内部合作历史 |
| 多候选 | 要求用户确认主体，不输出完整 CRM 锚定结论 |
| 只有弱接触记录 | 只写内部接触摘要，不上升为合作深度结论 |
| 字段权限不足 | 记录权限缺口，不绕过权限 |
| 内部样本不足 | 不输出强内部合作结论，只说明信息不足 |

快速检索未命中不等于 CRM 未覆盖；必须完成对象识别、对象描述和记录查询后，才能说明当前 CRM 证据不足。

## 7. 边界

- 不输出对象 API 名。
- 不输出内部记录 ID。
- 不输出敏感字段原值。
- 不给 CRM 动作建议。
- 不把我方产品、报价或销售动作写进客户合作历史结论。
