# 外部来源规则

本文定义 `account-cooperation-history` 如何使用公开来源。内容参考原始 `cooperation-history-report.zip` 和 `customer-intelligence-bidding.zip` 中可复用的合作、招投标和公开案例思路，并按当前专题 Skill 边界收敛。

## 1. 外部资料定位

外部资料用于回答以下问题：

- 客户过去和哪些企业发生过合作。
- 这些对象分别扮演什么角色，合作集中在哪些业务方向。
- 客户是否存在长期供应商、竞品占位、强绑定生态或公开项目合作关系。
- 招投标、采购、中标和项目参与事件反映了客户什么样的合作模式。

使用原则：

- 先锚定目标客户主体，再采公开合作证据。
- 招投标能力并入合作历史，不单独输出投标策略。
- 企业情报 CLI 和结构化招投标/公告来源优先使用；CLI 不存在、字段不足、返回为空、覆盖不全或角色解释不够时，才继续用 web search、官网、公告和权威公开来源补查。不要在未尝试 `market bidding-pinganzhengxin` 和 `market get-news` 时直接泛化 web search。
- 外部公开事件必须保留来源、时间和角色解释。
- 公开资料只用于客户合作理解，不输出采购推进、投标动作或销售方案。
- 资料不足时进入 `gaps`，不得编造合作事件、供应商关系或竞品占位。

## 2. 来源类型与证据要求

| 维度 | 优先来源 | 证据要求 | 可支撑内容 |
|:---|:---|:---|:---|
| 招投标/采购/中标 | 政府采购、招投标公告、采购公示、中标公示 | 事件名称 + 角色 + 时间 + 来源 | 项目合作、采购偏好、供应商关系 |
| 战略合作/签约 | 官网、公告、权威新闻 | 合作对象 + 合作内容 + 时间 | 战略合作、生态合作、联合方案 |
| 官网案例 | 企业官网案例、客户案例、解决方案页面 | 页面标题 + 页面时间/抓取时间 | 客户案例、行业应用、已落地项目 |
| 上市公司公告 | 重大合同、合作公告、年报 | 标题 + 日期 + 披露主体 | 合作强度、金额、长期协议 |
| 供应商/生态合作 | 官网伙伴页、联合公告、权威新闻 | 对象 + 关系性质 + 时间 | 供应商、渠道、生态伙伴 |
| CRM 外公开补证 | 搜不到结构化来源时的 web search | 来源 + 时间 + 可回链正文 | 补足公开合作线索，不替代权威证据 |

## 3. 角色和事件解释规则

- 公开合作事件必须区分采购方 / 中标方 / 参与方 / 供应商 / 生态伙伴 / 项目方 / 竞品或替代方。
- 不能只列企业名或项目名，必须说明角色和合作性质。
- 招投标或项目事件默认解释为“发生过项目关系”，不自动上升为长期框架合作。
- 供应商或竞品判断必须有合作内容、产品/服务描述或角色证据；仅凭名称不得硬判。

## 4. 证据优先级

合作专题的外部证据优先级为：

1. 招投标、采购、中标原文和上市公司正式披露。
2. 企业官网、企业公告、交易所公告、监管公开信息。
3. 权威新闻、权威案例报道、协会或政府项目公示。
4. 一般 web 新闻和公开转述。
5. 行业规律推断或名称启发式。

规则：

- 1-2 级可以直接支撑正式合作结论。
- 3 级可以支撑中强度判断，尽量寻找 1-2 级补证。
- 4 级仅用于补线索，最好不单独支撑强结论。
- 5 级只能标 `inferred` 或进入 `gaps`。

## 4A. web search / web fetch 控制

- 默认先用 `market bidding-pinganzhengxin`、`market get-news` 和上市公告；web search 只用于 CLI 证据不足、需要官网/公告原文补证或用户明确要求公开来源时。
- 每轮合作历史专题默认最多 1-2 个精准 query，每个 query 只消费前 3-5 条高质量结果；query 应包含企业全称、合作对象、项目名、招投标或公告关键词，避免泛搜“合作历史/供应商/行业地位”。
- web fetch 只抓官网、公告、监管、交易所、招投标原文和权威新闻。遇到“操作过于频繁”、访问受限、登录/验证码、403、404、加载失败、明显反爬或长时间无正文时立即降级，不反复等待或换同类页面重试。
- `market get-news` 或招投标 CLI 的摘要已足以支撑事实时，不为获取低质量二手网页正文长时间 fetch。

## 5. 时间窗与覆盖范围

| 来源域 | 默认时间窗 | 使用优先级 |
|:---|:---|:---|
| 招投标、采购、中标 | 近 12-24 个月 | 金额较大、主营相关、权威来源 |
| 战略合作、官网案例、联合公告 | 近 12-36 个月 | 与主营业务和客户重点相关 |
| 上市公司公告、重大合同 | 最近 1-2 个报告期 | 正式披露优先 |
| 一般新闻和公开案例 | 近 6-12 个月 | 最近且信息完整 |

规则：

- 时间范围由用户指定时，以用户要求为准。
- 只拿到旧资料时，标注“最新可得资料为 <时间>”。
- 非全量列表需要在 `meta.retrievalCoverage` 中记录覆盖范围；正文只在影响理解时表达。

## 6. 去重与合并

- 同一项目在公告、新闻、官网案例中重复出现时，按同一事件归并。
- 优先保留角色最清楚、原文最完整、时间最明确的来源。
- 招投标、采购和中标事件的合并与角色区分按 `bidding-merge-rules.md` 执行。
- 同一合作对象在多个时期多次出现时，可以拆成多条时间线事件，但摘要中应合并解释其关系强度。

## 7. 能力降级

| 情况 | 处理 |
|:---|:---|
| 权威公开来源不可用 | 转官网、公告、权威新闻补查，并降低判断强度 |
| 只有新闻转述 | 不作为唯一强证据，需继续找官网、公告或招投标原文 |
| 供应商类型不清 | 进入 `gaps`，不强下供应商或竞品结论 |
| 只找到旧项目 | 标注最新可得时间，不把旧项目写成当前重点 |
| 来源冲突 | 保留冲突来源和时间口径，降低判断强度 |
| CLI 返回为空、字段不足或覆盖不全 | 少量精准 web search、官网、公告、招投标原文和权威新闻补查；公开来源仍无证据时再进入 `gaps` |

## 8. 写入规则

- 公开合作事件写入 `cooperationHistory[]`。
- 供应商、竞品、替代关系、合作偏好和进入壁垒信号写入 `cooperationContext.supplierAndCompetitorSignals`。
- 公开合作对客户经营、需求、风险和相关信号的影响写入 `cooperationContext.businessImplications`。
- 与发问方业务相关的客户侧合作信号写入 `sellerRelevantSignals`。
- 证据统一写入顶层 `evidence`，正文字段用 `evidenceRefs` 回链。
- 角色不清、证据不足、资料过旧或来源冲突优先写入 `cooperationContext.gaps`，必要时同步写入顶层 `gaps`。
