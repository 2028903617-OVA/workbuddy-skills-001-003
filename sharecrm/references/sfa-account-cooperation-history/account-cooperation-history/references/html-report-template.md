# HTML 客户合作历史分析模板

本文定义 `account-cooperation-history` 的 HTML 输出形态。最终输出边界、数据消费顺序、章节裁剪和证据展示规则以 `output-contract.md` 为准；本模板只负责 HTML 展示结构。HTML 结果用于 CRM 页面展示、浏览器预览、打印或转 PDF，内容必须消费同一份 `schemas/standalone-report-data-model.md`，不得新增文字版结果没有依据的事实。

## 输出原则

- HTML 结果是正式展示形态，不是另一套分析逻辑。
- HTML 章节与 `output-contract.md` 的独立输出模板保持一致，并根据已有信息动态裁剪。
- 使用完整 HTML 文档结构和内联 CSS，避免外部依赖。
- 可使用少量内联 JavaScript 仅做目录锚点高亮和滚动跟随，不得异步加载、改写或补充报告内容。
- 样式应偏正式业务分析，适合 CRM iframe、富文本预览、浏览器打开和打印。
- 可打印、可转 PDF，避免依赖屏幕交互才能理解内容。
- 每个一级章节必须包含：开头概述结论、明细内容、末尾业务含义总结。

## 内容一致性

HTML 结果必须与文字版共享：

- 同一份目标客户主体。
- 同一份 `cooperationContext`、`cooperationHistory`、`sellerRelevantSignals`、`gaps` 和 `evidence`。
- 同一份 `meta.retrievalCoverage` 覆盖范围说明。
- 同一套事实 / 推断 / 待核实边界。
- 同一套脱敏和禁止展示规则。

HTML 可以用摘要块、时间线表格和证据标签提升可读性，但不能额外编造合作事件、供应商关系、竞品占位、内部历史或卖方信息。

## 标签来源规则

- HTML 中的标签、徽章和 emoji 文案必须来自 `schemas/standalone-report-data-model.md` 中已有字段、`cooperationContext`、`cooperationHistory`、`sellerRelevantSignals`、`gaps` 或可回链 `evidence` 的事实/归纳。
- 合作对象类型、合作来源、供应商/竞品、内部历史、机会、壁垒和风险标签必须来自合作事件、CRM 内部记录、招投标、公告、新闻、官网案例或明确模型归纳；不得把未核实对象写成已合作供应商、竞品或既有客户关系。
- 荣誉/资质标签仅在主报告传入的资质字段、企业情报 CLI 结果或公开证据明确支持时展示；不得仅凭行业、合作事件或客户规模生成“高新技术企业”“专精特新”“单项冠军”等标签。
- 模型归纳标签必须能回链合作事件、CRM/公开证据或 `sellerRelevantSignals`，并在正文或图例保留归纳口径。

## 视觉表达自由度

不要把 HTML 结果限制成纯白卡片和普通表格。允许模型根据合作事件数量、对象类型和时间跨度自由选择更有解释力的视觉表达：

- 封面可以使用品牌色、行业感配色、渐变背景、浅纹理或几何层次，并与正文 section 明显区分。可使用深色封面，但避免深色封面和深色全高目录同时占据过大面积。
- 封面可采用通栏背景 + 限宽内容，也可采用受控限宽封面；不固定标签数量、KPI 数量、摘要卡样式或副标题句式，只要求首屏有明确层次和视觉重点。
- 允许使用 emoji 或 Unicode 图标作为轻量视觉锚点，用于目录标题、合作结论、时间线节点、供应商/竞品标签、风险/机会信号和图表标题。
- 允许使用合作时间轴、客户类型分布图、招投标趋势组合图、关系网络图、Sankey、矩阵图、热力图、指标卡等表达合作关系、项目来源、对象角色和合作强度。
- 在“合作业务领域分布”结构化信息充分时，允许扩展输出“合作对象行业分布”和“合作对象区域 / 市场分布”；默认优先行业分布，其次区域 / 市场分布。
- 允许将强/中/弱、公开证据/内部记录/待核实、机会/壁垒/风险等模型归纳可视化，但必须标注归纳口径，不得伪装成原始统计值。

边界：不为视觉效果发明合作事件、供应商关系、竞品占位、金额、CRM 记录或卖方信息。

## 图表尺寸与复杂图表规则

- 不要让时间线、趋势组合图、关系网络图、Sankey、热力图全部复用普通图表的 360-380px 高度。普通图表建议 `min-height: 360px`；关系网络/Sankey 建议 `min-height: 500-620px`；热力图/矩阵建议 `min-height: 440-500px`；移动端不得低于 `400px`。
- 图表初始化前容器必须已有稳定宽高；窗口尺寸变化时调用 `chart.resize()`。
- 合作历史优先使用时间线、趋势组合图、关系卡和分组矩阵。只有存在清晰方向关系，例如“采购方 -> 项目/品类 -> 供应商/服务商”，才使用 Sankey；不得为图表编造交易流向、金额或合作强度。
- 真实金额、次数、项目数可作为图表值；只有定性强弱或证据等级时，必须标注模型归纳口径，不得伪装成原始统计值。
- 热力图/矩阵必须有清晰二维维度，例如“合作对象类型 x 合作内容”“业务领域 x 证据强度”。维度不足或标签过长时，改用关系卡、分组表格或时间线。
- 合作对象类型、合作来源、业务领域等真实构成占比清晰且类别少时，可用环形图/饼图；类别多、名称长、需要排序比较或样本不完整时，优先横向条形图、分组表格或关系卡。不得用饼图表达不完整样本、模型归纳占比或无证据的合作强度。
- 每个复杂图表必须有 fallback table 或文字结论，保留合作对象、角色、事件、时间、证据和归纳口径。
- 每个真实图表下方都必须附对应详细表格；不得把详细表格仅作为 fallback 保留。

## 长文档目录规则

- HTML 结果应为实际渲染出的章节生成目录；没有渲染的章节不得出现在目录中。
- 桌面端默认优先使用封面下方的横向 sticky 目录，让时间线、趋势图和关系图获得更宽展示空间；章节很多或标题很长时，可改用侧栏 sticky 目录。
- 横向目录宜使用浅色、半透明白或低饱和底色，当前章节用下划线、浅底或细色条高亮；避免默认使用深色全高侧栏。
- 移动端目录优先保持顶部 sticky 横向滚动；必要时可折叠成紧凑目录，不能遮挡正文。
- 目录项点击后跳转到对应 `section id`，正文应设置 `scroll-margin-top`。
- 目录高亮可使用少量内联 JavaScript 或 `IntersectionObserver`，脚本只允许控制目录状态。

## 样式规则

- 使用简洁正式但有视觉完成度的版式：清晰标题、紧凑段落、表格、摘要块、时间线、关系卡和高信息密度图表。
- 适合 CRM 工作台阅读，不做营销页、海报页或花哨动效。
- 使用 `max-width` 控制正文宽度，打印时移除多余阴影和背景。
- `合作时间线` 优先使用时间线或趋势组合图；合作对象、业务领域和供应商关系可使用分布图、关系网络图、矩阵或表格增强展示。
- “合作业务领域分布”章节在信息充分时，可继续拆分为合作对象行业分布和合作对象区域 / 市场分布；若证据不足，则仅保留业务领域分布或区域 / 市场分布，不强行补齐。
- `CRM 内部历史接触摘要` 和 `证据来源` 可用表格或摘要卡展示，避免整页只有表格。
- `合作历史情报结论`、`供应商关系与合作偏好` 和 `机会信号与壁垒信号` 优先用摘要块展示。
- 时间线、分布图、趋势图、关系网络图和 Sankey 下方必须有详细表格，至少覆盖对象、角色、事件、时间、业务领域、证据和归纳口径。
- 首屏应优先形成“封面 + 合作结论摘要 + 至少一个关键时间线/分布图/关系图 + 对应明细表”的组合，而不是只放长时间线或大表格。
- 长报告使用悬浮目录 + 正文布局；默认横向 sticky 目录，侧栏目录作为长目录备选。
- 允许封面使用大面积背景色或渐变；正文避免无关装饰、复杂动画、外部字体和不可控外部图片。深色应作为重点视觉层，不应同时覆盖封面和整条目录栏。

## CRM 内嵌展示规则

- 默认宽度按 CRM 内容区适配，推荐正文容器 `min-width` 不超过 980px。
- 可使用侧边或顶部目录辅助长文档阅读，但正文必须在没有交互时仍可顺序阅读。
- 首屏优先展示 `合作历史情报结论` 和最近阶段最关键的合作结论，避免先看到过长时间线。
- `合作时间线` 默认按时间倒序呈现，表格列数要受控；长文本优先换行，不做横向超宽表。
- `CRM 内部历史接触摘要` 只展示业务摘要、结果和对当前判断的影响，不展示对象 API 名、内部记录 ID 或敏感字段原值。
- `meta.retrievalCoverage` 仅在覆盖度会影响结论理解时，以简短提示块展示。

## 章节渲染规则

- 章节只在对应数据存在时渲染。
- 无数据章节不输出占位文案，例如“暂无”“未获取到”“待核实”。
- `待核实事项` 只在确实存在、且会影响关键判断时渲染。
- `证据来源` 只展示业务可读来源名称、时间和支撑内容。
- 同一条证据可以被多个合作事件引用，但在证据区只出现一次。
- 若章节中出现合作对象行业分布或区域 / 市场分布图，必须同步给出对应详细表格和业务含义总结。

## 脱敏和禁止展示

HTML 结果不得展示：

- 卖方画像原文、配置 CLI 原始返回值、卖方产品清单或能力说明。
- CLI 路径、SQL、对象 API 名、CRM 记录 ID 等技术追溯信息。
- 联系人手机号、邮箱、身份证等个人敏感信息。
- 内部备注、审批意见、成本、折扣、底价、合同条款、订单明细等敏感商业信息。
- 触达路径、销售话术、跟进节奏、作战计划、CRM 动作建议、新建商机/线索/联系人建议或投标推进方案。

## HTML 交付前自检

- 生成 HTML 结果后，交付前必须做一次展示完整性自检。
- 自检重点包括：目录项是否只对应实际渲染章节、锚点跳转是否有效、sticky 目录是否遮挡正文、表格/摘要块/时间线/关系卡是否完整。
- 如使用 ECharts、内联 SVG 或 JavaScript 图表，必须检查容器高度、数据字段引用、`series`、`legend`、时间轴节点和 fallback 内容是否一致。
- 不得保留空白图表容器、无效锚点、脚本报错后不可读的图表区域，或因目录层遮挡导致无法阅读的正文。
- 如图表无法稳定渲染，必须改为表格、列表、时间线、关系卡、矩阵或文字摘要表达同一数据。
- 每个一级章节是否都具备开头概述结论和末尾业务含义总结。
- 每个真实图表下方是否都有对应详细表格，而不是只有 fallback table。
- 自检只用于修复 HTML 呈现问题，不新增客户事实，不改变原有判断，不补写没有证据的合作事件。

## 打印和交付

- HTML 文档应可直接保存为 `.html` 文件。
- 文件名必须使用 `客户合作历史分析-<企业简称或工商全称>-<YYYYMMDD>.html`。
- 打印样式应保证标题、表格和证据来源可读。
- 如果运行环境不能创建 HTML 文件/附件，默认仍返回完整 HTML 内容或说明生成失败原因；只有用户明确要求 Markdown/文字版时才改为 Markdown/文字交付。可以创建文件时，文件对象应作为内部产物或附件卡片返回，不在最终回复正文中打印原始文件对象 JSON、内部路径或 `{"type":"file","path":"..."}`。
