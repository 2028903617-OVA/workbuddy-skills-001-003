# account-due-diligence-report

## Goal

作为客户情报 Agent 中的总控合成型 Skill，围绕目标企业主动获取、整合和分析内外部客户情报，输出结构化、可追溯、可用于业务判断的客户尽调报告。

本 Skill 综合客户主体、主营业务、经营状态、行业环境、产业链位置、合作历史、风险信息、CRM 内部记录以及发问方/卖方画像等信息，帮助不同角色理解：

1. 这个客户是谁。
2. 这个客户做什么。
3. 客户当前业务重点是什么。
4. 客户所在行业、产业链、合作关系、风险信息中，哪些内容与发问方业务相关。
5. 这些情报对客户理解、销售判断、方案准备、客户经营或签约风控有什么影响。

该 Skill 的输出重点是把获取到的客户情报组织成清晰的客户认知、业务解释和情报信号，而不是简单堆叠企业资料。

## Trigger

适合：

- 用户要求生成某个企业的客户尽调报告、客户情报报告、客户背景报告。
- 用户说"帮我看看 XX 公司""分析一下这个客户""这个客户是什么情况"。
- CRM 客户详情页需要生成客户画像或客户情报报告。
- 销售或销售管理者需要了解目标客户基本面、业务、行业位置、合作关系和风险。
- 售前需要理解客户业务场景、组织复杂度、产业链位置和潜在系统相关信号。
- 客户成功需要了解客户经营状态、合作历史、扩容/续费相关背景。
- 风控或签约角色需要了解客户主体、股权、司法、经营异常、账期和签约风险。
- 其他 Skill 需要先获得一份完整客户情报报告作为后续分析输入。

不适合：

- 只要求生成完整行业市场报告：应使用行业分析 Skill。
- 只要求分析某行业产业链全景：应使用产业链分析 Skill。
- 只要求分析历史合作、供应商或竞品关系：可直接使用合作历史 Skill。
- 要求输出触达路径、销售话术、跟进节奏、作战计划、谈判策略：应交给后续动作类 Skill。
- 要求做证券投资建议、股票买卖判断、财务投资评级。

## Inputs

| 输入 | 作用 | 必填 |
|:---|:---|:---|
| 目标企业名称 | 确定报告分析对象；可以是工商全称、简称、品牌名或 CRM 页面名称 | 是 |
| 主体辅助锚点 | 股票代码、统一社会信用代码、官网、所在城市、行业/业务关键词、用户明确提到的上市/集团/子公司身份，用于简称和多主体消歧 | 否；用户提供或上下文可得时必须使用 |
| 用户角色 | 判断报告重点，如销售、销售管理者、售前、客户成功、风控/签约 | 否，默认销售 |
| 用户业务场景 | 判断报告偏向客户开发、客户经营、售前准备、续费、签约风控等 | 否 |
| 发问方/卖方画像 | 通过系统配置 CLI 读取 `service_models`；缺失时按规则使用明确上下文或 CRM 产品/已成交摘要，用于判断哪些客户事实与发问方业务相关 | 运行时应尽量获取 |
| 内部企业情报 CLI 可用性 | 决定工商、股权、风险、经营等企业情报应调用哪些内部 CLI | 有 CLI 能力时必用 |
| CRM 客户记录 | 基于对象识别和对象描述查询预设对象，补充内部客户阶段、负责人、历史互动、商机、合同/订单、联系人等 | 有权限时应获取 |
| 外部企业情报数据 | 工商、股权、分支、风险、新闻、公告、招投标、年报等；内部 CLI 优先，缺失时公开 web 来源补查 | 有可用工具时应获取 |
| 行业分析结果 | 提供行业环境、趋势、政策、竞争格局、行业痛点摘要 | 需要行业背景时调用 |
| 产业链分析结果 | 提供目标客户上下游、生态关系、产业链位置 | 需要业务链路判断时调用 |
| 合作历史结果 | 提供公开合作、供应商、竞品、招投标、内部历史接触 | 需要合作关系判断时调用 |

## Scope

本 Skill 负责：

- 识别目标客户主体。
- 获取并整合客户内外部情报。
- 编排行业分析、产业链分析、合作历史等专题 Skill。
- 读取发问方/卖方画像用于内部推理。
- 按角色和场景生成客户尽调报告。
- 输出与发问方业务相关的客户侧情报信号。
- 保留关键证据来源。

本 Skill 不负责：

- 输出完整市场洞察报告。
- 输出行业静态全量报告或动态周报。
- 输出完整销售触达路径。
- 输出销售话术、跟进节奏、作战计划。
- 输出最终商机推荐或资源投入决策。
- 替代风控系统做最终授信/准入结论。
- 替代证券研究或投资建议。

## Output

默认交付方式为：先输出文字业务概要结论，同时交付一份 HTML 客户尽调报告作为正式完整结果。若用户未明确要求完整 Markdown/文字长文，不生成整份 Markdown 报告；Markdown 仅在用户明确要求时作为补充交付。

CRM 详情页、浏览器预览或正式交付场景中的 HTML 报告必须包含悬浮目录和数据可视化模块。悬浮目录、图表和摘要可视化优先消费 `references/schemas/report-data-model.md` 中已有字段；允许基于已有证据做明确标注的定性归纳可视化，但不得为了展示效果编造客户事实、金额、份额、排名、风险记录或合作关系。

正式输出必须先遵守 `references/output-contract.md`。文字版报告结构以 `references/report-template.md` 为准；HTML 报告结构以 `references/html-report-template.md` 为准。两种形态必须消费同一份 `references/schemas/report-data-model.md`，事实、证据和边界保持一致。

生成 HTML 前必须已经读取 `references/html-report-template.md`。如果本轮没有读取该文件，不得生成正式 HTML 文件，不得宣称 HTML 自检通过；应先读取模板后再继续。`html-report-template.md` 是展示规范和质量门禁，不是固定页面骨架；不得机械照抄其中的默认代码示例来替代面向当前客户的正式报告设计。

报告通常包含：

1. 客户概览摘要
2. 客户主体与基础信息
3. 集团、股权与组织关系
4. 主营业务与商业模式
5. 行业环境与客户位置
6. 产业链与生态关系
7. 经营动态与业务重点
8. 上市主体公开财务与经营摘要（适用时）
9. 合作历史与供应商关系
10. 风险与准入信息
11. 与发问方业务相关的情报信号
12. 证据来源

输出要求：

- 根据获取到的信息动态裁剪章节。
- 没有获取到的信息不强行输出。
- 不在报告开头固定输出"证据缺口"或"待核实事项"。
- 不展示卖方画像原文。
- 不输出详细触达、推荐动作、话术或作战计划。
- 重要判断应有证据来源支撑。
- 模型推断应与事实分开表达。
- HTML 报告不得新增文字版没有依据的事实，只能改变呈现形态。

## Core Rules

### 1. 企业锚点消歧是前置步骤

生成报告前必须确认目标企业主体。优先按 `references/enterprise-cli-map.md` 中的工商基础 CLI 取得工商全称、统一社会信用代码和行业。

如果用户输入存在明显歧义，例如简称、品牌名、多主体并存，或工商基础 CLI 的唯一命中与用户上下文中的上市身份、股票代码、行业/业务关键词、官网、城市不一致，应继续做候选补查或先返回候选主体让用户确认；无法判断主体时，不生成完整报告。

主体确认后，后续企业情报 CLI、CRM 预检和专题 Skill 编排统一使用确认后的工商全称、统一社会信用代码和必要的主体口径说明，不继续使用原始简称作为默认查询主体。

### 2. 企业情报数据优先调用内部 CLI，并用公开来源补查

当报告需要企业基础工商、股权结构、分支机构、对外投资、主要人员、经营异常、行政处罚、司法风险、税务风险、破产、严重违法、上市公司信息、公开动态或舆情提及等企业情报数据时，应优先按 `references/enterprise-cli-map.md` 调用内部 CLI。

当内部 CLI 不存在、报错、返回为空、字段不足，或无法覆盖用户明确关注的数据域时，应继续通过 web search、企业官网、公告、年报、监管网站、新闻、招投标网站等公开来源补查。

内部 CLI 是第一优先级，不是唯一来源。不得绕过已定义 CLI map 自行臆造数据来源、字段含义或调用参数；也不得因为 CLI 返回为空就直接断言该事项不存在。公开来源仍无证据时，该类信息动态裁剪不输出。

### 3. 卖方画像只参与推理，不作为报告内容展示

发问方/卖方画像用于判断哪些客户事实与发问方业务相关。报告中不能直接展示卖方公司介绍、产品清单、能力说明或销售卖点，只能输出基于卖方画像推理后的客户侧情报信号。

具体规则见 `references/seller-context-rules.md`。

### 4. 不假设卖方行业

本 Skill 面向商业化 CRM 系统，发问方可能来自任意 B2B 行业。所有"与发问方业务相关"的判断必须基于实际读取到的卖方画像、CRM 上下文或用户输入，不得默认发问方是 SaaS、CRM 或企业服务厂商。

### 5. CRM 查询必须对象描述驱动

CRM 内部数据优先查询预设对象，如客户、联系人、商机、销售合同、销售订单、回款和销售记录。查询前必须先识别对象并获取对象描述，根据当前租户真实字段 label、类型、选项和关联关系解释业务含义。

不得固定假设某个字段 API 名一定存在。自定义对象不作为第一版默认查询范围；只有用户明确要求或预设对象不足以解释合作历史时，才按 `references/crm-cli-map.md` 探索。

### 6. 报告基于已获取信息输出

报告不追求模板项完整，而追求信息有效。没有获取到的信息默认不写；不得为模板完整性强行输出"暂无信息""未获取到""待核实"。

如果某个用户明确要求的点无法确认，可以在对应位置简短说明无法确认。

### 7. 不编造事实

不得编造企业工商信息、主营业务、股权和集团关系、合作历史、供应商或竞品关系、风险记录、CRM 内部记录、卖方画像或内部成交案例。

### 8. 专题 Skill 结果必须按客户报告目标裁剪

行业分析、产业链分析、合作历史等专题 Skill 可以独立工作，也可以被本 Skill 编排调用。被编排调用时，本 Skill 只消费与目标客户报告相关的摘要、判断和证据，不直接拼接完整专题分析结果。

### 9. 风险和合作信息必须解释业务影响

风险信息不能只罗列记录；合作历史不能只列新闻。凡输出风险、合作、供应商、竞品或内部历史接触信息，都应说明其对客户理解、销售判断、方案准备、客户经营或签约风控的影响。

### 10. 不输出动作类方案

本 Skill 可以输出情报信号和业务解释，但不输出触达路径、具体找谁、销售话术、跟进节奏、作战计划、谈判策略或推荐动作清单。

## Workflow

详细流程以 `references/00-workflow.md` 为准。主执行骨架如下：

1. 确认目标企业主体，完成简称、多主体、上市/集团/子公司身份等锚点消歧。
2. 识别用户角色和业务场景，必要时读取角色裁剪规则。
3. 读取卖方画像或可用降级来源，仅用于内部相关性推理。
4. 按 CLI map 和公开来源采集工商、股权、分支、对外投资、人员、业务、动态、风险、上市和 CRM 内部记录。
5. 客户尽调正式报告默认编排行业分析、产业链分析、合作历史三个专题 Skill；跳过必须记录原因。
6. 将所有阶段产物归入 `schemas/report-data-model.md`，记录取数覆盖、证据和专题读取状态。
7. 按 `output-contract.md` 裁剪最终内容；文字版读取 `report-template.md`，HTML 版读取 `html-report-template.md`。
8. 输出前读取 `quality-checklist.md` 做内部自检；自检结果不得作为报告章节输出。

生成 HTML 时必须先读取 `references/html-report-template.md`。该文件是展示规范和质量门禁，不是固定页面骨架；不得机械照抄片段来替代面向当前客户的正式报告设计。

## Notes

- 本 Skill 是客户情报 Agent 的主报告 Skill。
- 行业分析、产业链分析、合作历史等专题 Skill 可以独立使用，也可以被本 Skill 编排调用。
- 行业分析在本 Skill 中只作为客户相关摘要，不承接市场洞察 Agent 的静态/动态报告机制。
- 报告应基于实际获取到的信息动态生成，不追求模板完整。
- 有价值的信息应尽量保留证据来源。
- 不确定内容不能伪装成事实。
