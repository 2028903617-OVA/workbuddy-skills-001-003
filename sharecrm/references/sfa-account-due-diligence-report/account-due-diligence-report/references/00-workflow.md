# 客户尽调报告执行流程

本文是 `account-due-diligence-report` 的主流程 reference。主 `SKILL.md` 负责入口，本文件负责执行顺序、降级规则和阶段产物。

## 阶段顺序

```text
用户输入目标企业
  ↓
BA. 企业锚点消歧（唯一前置中止点）
  ↓ 工商全称 / 统一社会信用代码 / 行业确认
A. 卖方画像读取 ─┐
                 ├─ 合并上下文
B. CRM 预检 ─────┘
  ↓
C. 企业外部事实采集（工商/股权/分支/投资/主要人员/风险/上市等）
  ↓
D. 主营业务与商业模式分析
  ↓
E. 按需调用行业分析 / 产业链分析 / 合作历史
  ↓
F. 形成 report-data-model
  ↓
G. 按输出契约生成报告
  ↓
H. 质量自检
```

## BA. 企业锚点消歧

企业锚点消歧是唯一会中止流水线的前置步骤。

执行要求：

1. 从用户输入和上下文抽取主体辅助锚点：股票代码、统一社会信用代码、官网、所在城市、用户提到的行业/业务关键词、是否上市、集团/子公司身份。
2. 用户输入是简称、品牌名、产品名、股票简称、缺少行政区划的公司名或 CRM 页面名时，先按 `enterprise-cli-map.md` 调用 `sharecrm intelligence company search` 做一次结构化候选召回；不要先进入 web search，也不要反复用多个企业信息 CLI 试错。
3. 如果候选主体与辅助锚点不一致，不得直接进入报告；应按辅助锚点继续核对上市公司简介、股票代码、官网或公开来源，或返回候选主体请用户确认。
4. 唯一高置信候选或用户确认后，再用 `sharecrm intelligence company conc` 的 `baseinfo` 等批量结果记录工商全称、统一社会信用代码、行业、登记状态、上市状态和主体确认依据。
5. 多候选时返回候选列表让用户确认；候选列表至少包含企业全称、统一社会信用代码或股票代码、行业、登记/上市状态和为什么可能匹配。
6. 无命中时提示无法识别企业主体。
7. 后续所有企业情报 CLI、CRM 预检和专题 Skill 统一使用已确认工商全称；原始简称只作为别名或补充检索词，不作为默认主体。

示例：

- 用户输入某公司简称，工商基础信息可能命中名称相近但行业不符的非目标主体；如果上下文提到上市身份、股票代码、官网或主营业务关键词，应继续确认目标上市主体或真实签约主体，不能直接基于名称相近主体生成报告。

## A. 卖方画像读取

目标是让报告具备发问方语境，但不把卖方画像展示在报告中。

按 `seller-context-rules.md` 读取卖方上下文，优先使用系统配置 CLI：

1. `service_models`

配置为空或不足时，按顺序使用用户输入或当前 CRM 页面上下文、CRM 产品/服务对象摘要、近 12-24 个月已成交合同/订单摘要作为降级来源。仍不足时，只做通用 B2B 谨慎解释。

阶段产物写入 `report-data-model.md` 的 `meta.sellerContext`：

- 读取状态和来源。
- 服务形态和内部降级来源摘要。
- 内部相关性判断摘要。
- 置信度和降级原因。

缺失处理：

- 卖方画像缺失时，仍可输出客户事实。
- 不输出产品/方案匹配判断。
- 不默认卖方是 SaaS、CRM 或企业服务厂商。
- 不在报告正文固定输出卖方画像缺失说明。

## B. CRM 预检

CRM 预检与卖方画像读取可并行。

按 `crm-cli-map.md` 查询 CRM 内部记录。CRM 字段允许租户自定义，执行时必须先识别对象、获取对象描述，再基于字段 label、类型、选项和关联关系选择字段。

第一版默认查询预设对象：

- 客户 `AccountObj`：目标客户是否已建档、负责人、公海/分配状态、客户阶段或成交状态。
- 联系人 `ContactObj`：联系人覆盖情况和可解释的角色信息。
- 商机 `NewOpportunityObj`：当前商机、历史商机、阶段、金额、输赢状态。
- 销售合同 `SaleContractObj`、销售订单 `SalesOrderObj`：历史成交、产品、金额、周期。
- 回款 `PaymentObj`、回款计划 `PaymentPlanObj`：回款和账期相关背景。
- 销售记录 `ActiveRecordObj`：近期互动和跟进活跃度。

自定义对象不默认扫描。只有用户明确提到，或预设对象不足以解释合作历史时，才按 `crm-cli-map.md` 的关联对象查询规则，从客户对象出发选择语义相关对象继续查询。

阶段产物写入 `report-data-model.md` 的 `crmContext`：

- 账户匹配状态。
- 当前内部覆盖和负责人/公海等状态摘要。
- 联系人、商机、合同/订单、回款、销售记录摘要。
- 字段解释依据和查询降级说明。
- 查询覆盖范围写入 `meta.retrievalCoverage`，不把首批结果当作全量结论。

缺失处理：

- CRM 查询失败不中止报告。
- 不把 CRM 缺失写成客户事实。
- 如果用户明确要求内部记录而未能获取，可在对应位置简短说明。

## C. 企业外部事实采集

优先使用 `enterprise-cli-map.md` 定义的内部 CLI。内部 CLI 是第一优先级，不是唯一来源。

以下情况必须继续通过 web search、企业官网、公告、年报、监管网站、新闻、招投标网站等公开来源补查：

- CLI 不存在或当前环境不可调用。
- CLI 返回 `FAIL`、报错或超时。
- CLI 返回空列表、`total=0` 或目标字段为空。
- CLI 字段不足，无法支撑用户明确关注的问题。
- 用户询问的是近期动态、公告、招投标、新闻、官网业务介绍等 CLI 不一定覆盖的信息。

公开来源补查仍无证据时，该数据域不输出；不得把 CLI 空结果写成确定的"不存在"。

企业列表类数据默认采用时间窗优先的首批取数策略：先按数据域和用户场景确定默认时间窗、排序或筛选条件，再获取首批记录。`pageNum=1` 只是执行参数，不代表业务覆盖范围。

如果首批记录足以支撑报告判断，不继续翻页；如果用户角色、用户问题或首批结果显示该数据域会显著影响结论，应优先通过筛选、排序、聚合或关键状态查询做定向补查，而不是机械全量翻页。

默认时间窗和优先级：

| 数据域 | 默认时间窗 | 首次获取优先级 |
|:---|:---|:---|
| 新闻/动态/公告 | 近 6-12 个月 | 最近、权威来源、与经营变化相关 |
| 招投标/中标 | 近 12-24 个月 | 最近、中标/采购金额较大、与主营业务相关 |
| 风险/司法/处罚 | 近 24-36 个月 + 当前未结清记录 | 未结清、高金额、失信、被执行、破产、重大处罚优先 |
| 股东/分支/对外投资 | 当前有效结构优先 | 主要对象、有效状态、能解释集团关系和区域覆盖的记录 |
| 荣誉资质/主要人员 | 当前有效优先 | 有效期内资质、当前任职、关键资质 |

追加查询仍应设置上限。默认不超过 2-3 页或 20-50 条关键记录；超过上限时输出总量、关键记录和业务含义，不展开全量明细。覆盖范围写入 `meta.retrievalCoverage`。

公开动态、新闻和舆情提及可以同时调用新闻类 CLI 与 `sharecrm intelligence market search-mentions`。调用 `search-mentions` 前必须读取 `search-mentions-cli.md`，按 `keyword`、来源、时间窗、分页、排序、匹配字段、情感、站点、用户和地域规则校验入参。该 CLI 的 `keyword` 是普通搜索词，不支持高级表达式、`should_kw` 或 `not_kw`；时间过滤固定为 `ctime`，默认时间跨度不超过 7 天。需要更长口径时按不超过 7 天的窗口分段查询，不发送大窗口。多来源动态结果进入 `operationDynamics` 和 `evidence` 前必须按 `report-data-model.md` 的动态去重规则合并。

数据域包括：

- 工商基础。
- 股权、实控、分支、对外投资。
- 主要人员。
- 荣誉资质。
- 知识产权与研发实力：专利、软件著作权、参与标准、商标、ICP备案；知识产权出质作为风险/融资补充，不混入研发实力结论。
- 新闻、公告、招投标、全媒体公开动态和舆情提及。
- 经营异常、行政处罚、司法风险、税务风险、破产、严重违法。
- 上市公司简介、公告、财务摘要。

### 上市财务采集补充

上市主体公开财务只在目标主体为上市公司、用户明确关注经营财务，或上市主体与签约主体关系对风险判断有影响时采集。采集前必须先确认上市主体与目标签约主体是否同一主体；不是同一主体时，只能表达“上市主体口径”，不得套用为签约主体财务。

上市财务三表命令在当前 CLI 1.1.8 下存在数值参数传递缺陷：`reportYear`、`pageNum`、`pageSize` 等 integer 字段即使通过 JSON number 或显式 flag 传入，也可能触发 `action input schema validation failed: string found, integer expected`；不带这些数值参数、仅传 `companyName` 时可稳定返回第一页列表，列表内通常包含多个 `reportYear/endDate/reportDateType/isAudit`。在 CLI 修复并重新验证前，默认策略如下：

1. 先用上市公司简介确认股票代码、上市状态和上市主体名称。
2. 查询利润表、资产负债表、现金流量表时，只传 `companyName`，不传 `reportYear`、`pageNum`、`pageSize`。
3. 在第一页返回列表中按 `reportYear`、`endDate`、`reportDateType`、`isAudit` 客户端筛选最近年度、最近季度或用户要求的期间。
4. 如果用户明确指定年份，先在第一页返回列表中筛选该 `reportYear`；命中则使用该记录并标注期间口径。
5. 如果用户指定年份未出现在第一页返回列表中，不得断言该年份没有财报，不再构造 `reportYear/pageNum/pageSize` 调用；应记录 `meta.retrievalCoverage.publicCompanyFinancials` 覆盖不足，并改用上市公告、交易所/巨潮公告、公司官网投资者关系、年报 PDF 或其他公开来源补证。
6. 如果后续 CLI 修复并经验证支持数值参数，可按最新 `--help` 使用 `reportYear/pageNum/pageSize` 精确查询或翻页；在未验证前不依赖这些参数。
7. 三表字段只用于经营、预算、履约和风险背景，不输出证券投资判断。

## D. 主营业务与商业模式分析

从已获取资料中抽取：

- 客户卖什么。
- 卖给谁。
- 怎么销售。
- 怎么交付。
- 当前业务重点和经营变化。
- 业务复杂度。

不要把行业常识直接写成客户事实。

## E. 专题 Skill 编排

客户尽调报告、客户情报报告、客户背景报告和客户详情页报告默认调用三个专题 Skill。不要因为主报告已经获取了基础企业事实，就跳过专题 Skill；专题 Skill 的价值是把行业、产业链和合作历史解释成客户理解结果。

编排前必须先读取 `references/skill-composition.md`，按其中 `minimumReferenceSet` 执行专题 references 深读和结果消费。只读取专题 `SKILL.md` 不等于完成专题执行。

默认编排：

- 行业分析 Skill：必须调用并只消费客户相关行业摘要、行业位置、趋势/政策/竞争/痛点判断、业务含义和证据。
- 产业链分析 Skill：必须调用并只消费目标客户链路、上下游、渠道、生态、集团/资本关系、关键依赖、业务含义和证据。
- 合作历史 Skill：必须调用并只消费合作对象、合作性质、供应商/竞品占位、招投标、CRM 内部历史关系、业务含义和证据。

专题执行硬门槛：

- 每个已调用专题必须读取 `skill-composition.md` 中该专题列出的最小 reference 集。
- 若专题只读取了 `SKILL.md`，该专题只能标记为 `topicInsights.<topic>.loadStatus=partial`，不得标记为完整可用。
- 若任何必读 reference 因权限、缺失、上下文或工具限制未读取，必须写入 `topicInsights.<topic>.referenceReadStatus` 的 `required/read/missing/status/downgradeReason`。
- 存在 `referenceReadStatus.status=partial | failed` 时，最终质量自检不得宣称专题编排全部通过；正式报告可继续生成，但相关专题判断必须降低确定性。

允许跳过的情况：

- 用户明确只要求主体、风险、CRM 内部记录等窄范围报告。
- 专题 Skill 当前不可用或执行失败。
- 目标主体无法识别，或基础事实不足以支撑该专题判断。
- 该专题与用户问题无关，且跳过不会影响报告完整性。

跳过时必须写入 `topicInsights.<topic>.loadStatus=not_called | missing`、`downgradeReason` 或 `gaps`，并在 `meta.retrievalCoverage` 记录原因。不得静默跳过。

## F. 形成 report-data-model

所有阶段产物先归入 `schemas/report-data-model.md` 定义的结构化中间数据。

报告模板只能消费数据模型中的已有内容，不补写不存在的事实。

## G. 按输出契约生成报告

先按 `output-contract.md` 执行最终输出裁剪和边界检查，再进入具体模板渲染：

- 文字版报告按 `report-template.md` 渲染。
- 需要 HTML 时按 `html-report-template.md` 渲染。
- 两种形态必须消费同一份 `schemas/report-data-model.md`，事实、证据和边界保持一致。
- `topicInsights` 只用于追溯专题 Skill 返回结果，正式报告优先消费 `industryContext`、`chainContext`、`cooperationContext` 等主报告字段。
- HTML 正式报告必须包含悬浮目录、章节锚点和可视化模块；如果某类图表因数据不足无法渲染，应使用可视摘要块或表格降级，而不是输出无图表的纯文本页面。
- HTML 渲染前，如分支机构、子公司、项目或客户等数据存在省份/城市、登记机关、地址或名称可推导地域字段，必须按 `html-report-template.md` 的地图硬规则先构造区域着色地图候选；分支机构总量在 100 家以内时应先取全量明细再聚合。不能在未尝试地图、未记录 `mapConfig.mapDataUrl/matchedRegions/downgradeReason` 的情况下直接输出圆点地图、柱状图或表格；分支机构不得用饼图替代区域地图，地图失败时用表格降级。

## 降级规则

| 情况 | 处理 |
|:---|:---|
| 企业多候选 | 中止，要求用户确认主体 |
| 企业无命中 | 中止，提示无法识别主体 |
| 卖方画像缺失 | 输出客户事实，不做强相关性判断 |
| CRM 预检失败 | 继续生成外部事实报告，不编造内部记录 |
| 某类 CLI 失败、为空或字段不足 | 继续 web search 补查；公开来源仍无证据时不输出 |
| 专题 Skill 不可用 | 继续生成主报告，但必须在 `topicInsights`、`gaps` 或 `meta.retrievalCoverage` 记录不可用原因；只基于已获取信息生成对应主题内容 |
| 证据不足 | 降低判断强度，不把推断写成事实 |
