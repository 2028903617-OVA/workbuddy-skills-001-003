# HTML 客户尽调报告展示规范

本文只定义 HTML 展示形态和质量门禁。最终输出边界以 `output-contract.md` 为准，数据字段以 `schemas/report-data-model.md` 为准。HTML 不得新增文字版没有依据的事实。

本文件不是固定页面骨架。不要机械照抄片段生成整页模板；应根据客户行业、数据密度和业务问题组织封面、目录、摘要、KPI、表格、矩阵、图表和证据。

## 必备结构

- 完整 HTML 文档，使用内联 CSS；可用少量内联 JavaScript 做目录高亮和图表渲染。
- 封面作为第一视觉层，呈现报告类型、目标企业、日期、行业/上市/状态等核心标签。
- 封面下方默认使用浅色横向 sticky 目录；目录项只包含实际渲染章节。
- 每个正文章节必须有稳定 `id`，目录链接使用 `href="#section-id"`。
- 正文按 `report-template.md` 的章节语义动态裁剪；无数据章节不输出占位文案。
- 每个一级章节必须包含：开头概述结论、明细内容、末尾业务含义总结。
- 证据来源放末尾，只展示业务可读来源、时间和支撑内容。

## 布局规则

- 封面优先作为顶部贯通的第一视觉层，不要默认做成普通圆角卡片；封面内容可与正文共享阅读宽度，但背景可横向贯通页面。
- “通栏封面”指封面背景层不受正文主容器宽度限制；封面内容层可限宽，但不得把封面整体继续包在与正文等宽的普通内容壳中伪装成通栏。
- 横向目录可使用全宽浅色 sticky 条，目录文字区域应与正文左右边界对齐；避免目录、封面、正文各自不同宽度导致页面松散。
- 外层容器控制整体阅读宽度；封面内容、目录内容和正文 main 默认同宽。
- 不要给 `.report`、`main` 或正文外层设置比外层容器更窄的 `max-width`，避免全屏时正文左右留白大于顶部。
- 横向目录应紧凑、浅色、可横向滚动，并通过下划线、浅底或细色条标识当前章节。
- 当章节很多、标题很长或横向目录明显拥挤时，可改用浅色侧栏 sticky 目录。
- 移动端目录优先保持顶部横向滚动；窄屏下摘要卡、KPI、图表网格改为单列。
- 打印时可隐藏目录，移除多余阴影和背景，保证标题、表格和证据可读。

关键 CSS 片段：

```css

.cover { width: 100%; }
.cover-inner { max-width: 1120px; margin: 0 auto; padding: 72px 32px 56px; }

.toc nav { display: flex; gap: 4px; white-space: nowrap; }
.report { min-width: 0; width: 100%; margin: 0 auto; }
@media (max-width: 860px) { .shell { padding: 12px; } }
@media print { .toc { display: none; } }
```

## 摘要与卡片

- 概览摘要使用 3-4 张结论卡解释“客户是谁 / 做什么 / 当前业务重点 / CRM 或合作状态”。
- `CRM 或合作状态` 结论卡只在 CRM 精确命中、别名命中且已确认、或有稳定内部记录支撑时展示；CRM 未命中、仅模糊候选或别名冲突未解决时，宁可省略该卡，也不要生成看似确定的 CRM 状态结论。
- 若渲染 4 张结论卡，桌面端使用 2x2：`grid-template-columns: repeat(2, minmax(0, 1fr))`。
- 不使用 `auto-fit + minmax` 导致常见宽度下出现 3+1。
- 卡片高度由内容自然撑开，不固定高度；必要时压缩摘要文案。
- KPI 行承载注册资本、成立时间、人员、分支、投资、知识产权、风险记录、合作金额等关键数字。
- 首屏应优先形成“封面 + KPI + 概览结论卡 + 至少一个高价值可视模块”的完整阅读节奏，而不是只放标题和长段文字。
- 封面标签数量、KPI 数量、摘要卡排布和首屏图表位置不固定，只要首屏具备正式报告感和清晰的信息主次即可。

## 章节结构规则

- 每个一级章节开头必须先给出 1-3 句概述结论，说明本章最重要的判断。
- 每个一级章节结尾必须给出 2-4 句业务含义总结，说明这些事实对客户理解、合作判断、风险判断或机会判断意味着什么。
- 概述结论和业务含义总结都必须基于本章事实和证据，不得新增无依据判断。
- 不得只展示图表、表格和长段资料而没有章节结论；也不得只有结论、没有事实支撑。

## 可视化规则

- HTML 必须包含悬浮目录、章节锚点、滚动高亮和至少一个来自 `visuals` 或结构化字段的可视化模块。
- 正式报告通常输出 2-4 个高信息密度可视化；数据较少时至少 1 个。
- 图表必须回答清晰问题，且比表格、列表或摘要块更易理解。
- 普通图表可继续优先使用成熟绘图库，例如 ECharts；地图边界数据源和地图清晰度按本文件的地图硬规则单独治理，不与普通图表共用同一稳定性假设。
- 图表数据必须来自 `visuals`、已有结构化字段，或显式标注的模型归纳；不得伪造金额、份额、排名、趋势、风险记录或合作关系。
- 不为凑数量生成低价值图表，例如专题覆盖饼图、无证据雷达评分、伪占比、伪趋势。
- 可视化应嵌入对应业务章节：股权图在组织章节，地图在组织/区域章节，产业链图在产业链章节，财务图在财务章节。
- 每个真实图表必须同时具备：图表本体、对应详细表格、fallback table 或文字结论。不得只有图没有表，也不得把详细表格仅作为脚本失败时才展示的 fallback。
- KPI 卡、摘要卡、标签组和信号卡不强制单独配表，但所在章节必须有明细表支撑。

图表尺寸规则：

- 不要让所有 ECharts 复用同一个 360-380px 高度。按图表类型设置稳定容器高度，避免地图、Sankey、热力图被压缩。
- 普通柱状图、折线图、饼图容器建议 `min-height: 360px`。
- 中国地图、省级地图和区域分布地图桌面端建议 `min-height: 580-620px`，不得低于 `560px`；移动端不得低于 `460px`。
- Sankey、分层流向图、关系网络图桌面端建议 `min-height: 500px`，节点多于 12 个时提高到 `560-640px`。
- 热力图、矩阵图桌面端建议 `min-height: 440px`；行列标签较多时提高到 `500px` 并给标签留足旋转或换行空间。
- 图表初始化前容器必须已有稳定宽高；窗口尺寸变化时调用 `chart.resize()`。

推荐 CSS 片段：

```css
.chart-container { width: 100%; min-height: 360px; }
.chart-container.map { min-height: 600px; }
.chart-container.sankey { min-height: 520px; }
.chart-container.heatmap { min-height: 460px; }
@media (max-width: 860px) {
  .chart-container.map { min-height: 460px; }
  .chart-container.sankey,
  .chart-container.heatmap { min-height: 400px; }
}
```

推荐表达：

| 内容 | 推荐表达 |
|:---|:---|
| 股权结构 | 默认优先环形图/饼图展示股东分布；有持股比例按比例画，比例不完整时按“已披露股东/投资方构成”标注口径；股东多或名称长时合并小项为“其他”并配明细表 |
| 分支/子公司/项目/客户区域分布 | 中国地图或省级地图区域着色图；分支机构不得使用饼图替代区域分布，地图失败时改用省份排行、区域分组表或明细表 |
| 经营动态 | 时间轴 |
| 研发与知识产权实力 | 知识产权结构卡、专利/软著/标准分组表或产品-技术矩阵 |
| 产业链关系 | Sankey、分层流向图或关系卡 |
| 风险信息 | 风险矩阵或分组清单 |
| 产品-场景-机会 | 热力图或定性矩阵 |
| 行业分布/行业事件类型/竞争格局/公开动态来源构成 | 热力图、定性矩阵、分组条形图、趋势组合图；真实构成类别少且样本完整时可用环形图/饼图 |
| 合作历史 | 时间轴、类型分布或关系卡 |

## Sankey 与流向图规则

当 `chainContext`、主营业务、供应链、渠道、应用场景或客户生态中存在明确方向关系时，优先考虑 Sankey 或分层流向图。

- Sankey 应回答“上游资源/能力如何流向产品、渠道、下游场景或客户群”这类问题，放在产业链或商业模式章节。
- 节点必须来自已有结构化字段、证据或明确标注的模型归纳；边的 `source`、`target` 必须能在节点中找到。
- 真实金额、采购量、项目数、招投标次数等可作为 `value`；没有真实流量值时，不得伪装成规模、份额或金额。
- 如果为了 ECharts 布局需要数值但只有定性关系，可使用统一布局值，并在图例或说明中标注“数值仅用于布局，不代表金额、份额或真实流量”，同时设置模型归纳口径。
- 方向关系不足、节点少于 3 层或边界不清时，不强行生成 Sankey，改用分层关系卡、链路表或定性矩阵。
- 节点过多时先按业务问题聚合到 8-15 个核心节点，避免生成不可读的毛线图。

## 热力图与矩阵规则

当 `industryContext`、`businessModel.productsOrServices`、应用场景、机会强弱、风险关注、客户匹配度或卖方相关信号存在二维结构时，优先考虑热力图或定性矩阵。

- 热力图应回答“哪些产品/能力匹配哪些场景、趋势或机会更强”这类问题，放在行业环境、主营业务或卖方相关信号章节。
- 行列维度必须语义清晰，例如“产品/能力 x 应用场景”“业务板块 x 行业趋势”“机会主题 x 证据强度”“行业事件类型 x 影响强弱”“竞争对象 x 对比维度”。
- 真实数量、金额、次数可直接入图；强/中/弱、高/中/低、已证实/推断/待核实等定性等级必须标注为模型归纳，并展示等级含义。
- 不得把模型归纳等级包装成真实评分、市场份额或客观排名。
- 维度少于 2x2、标签过长导致不可读、或证据不足时，改用定性矩阵、关系卡或表格增强。
- 热力图必须提供 fallback table，保留行、列、等级/数值和依据说明，保证脚本不可用时仍可读。

行业章节图表规则：

- 行业章节只要结构化信息充足，至少输出一个行业图表；不得在整份报告已有其他图表的情况下，把行业章节长期降级为只有文字和表格。
- 行业竞争格局、行业事件类型、公开动态来源构成、产品/场景/机会匹配、行业变化影响等内容，应优先选择分组条形图、趋势组合图、热力图或定性矩阵。
- 只有证据不足、维度不清或样本过少时，行业章节才允许退回纯表格表达，并在正文中保留降级说明。

## 地图硬规则

区域分布只要存在省份/城市字段，默认优先尝试 ECharts `map` 区域着色图。

- ECharts 5 不内置中国地图数据；必须加载公司内部公网可访问地区边界 GeoJSON、平台内置地图数据或内嵌合法 GeoJSON/SVG，并执行 `echarts.registerMap`。
- 默认使用公司内部地区边界地址 `https://a9.fspage.com/FSR/weex/sfa/resource/map_boundary.json`；只有该地址不可用时，才退回平台内置、本地资产或内嵌地图数据，不再依赖外部开源公网 GeoJSON。
- 不得让 LLM 读取、粘贴或生成 GeoJSON 全文。
- `series` 必须包含 `type: 'map'`，且 `series.map` 与 `registerMap` 的 `mapName` 一致。
- `data` 使用地图口径一致的完整省级/直辖市/自治区/特别行政区名称，例如 `浙江省`、`北京市`、`广西壮族自治区`。
- 城市字段先归一到省级行政区，再与 GeoJSON 的 `properties.name` 匹配；必须记录 `matchedRegions` / `unmatchedRegions`，存在未匹配地区时不得判定地图成功。
- 常见简称或缺后缀返回值必须先归一为地图口径再入图，例如：`北京 -> 北京市`、`广东 -> 广东省`、`广西 -> 广西壮族自治区`。不要在模板中展开过长映射表，运行时按中国省级行政区标准名称处理。
- 当分支机构或项目返回里缺少显式省份字段时，允许优先从登记机关、分支名称、详细地址或已确认城市字段推导省级行政区；如果无法稳定归一，就降级为区域表、排行表或明细表，不强行绘制疑似错误的地图。
- 如果图表表达对象是分支机构，`data.value` 必须是按省级行政区聚合后的分支机构数量；不得把“是否覆盖”伪装成数量着色图。分支机构总量在 100 家以内时，应先分页取全量明细再聚合；无法取全时不要输出“首批地图”，应降级为表格并说明取数限制。
- 分支机构不得用状态饼图、类型饼图或注销/存续占比图替代区域地图；如确需展示状态分布，只能作为地图或明细表之外的补充摘要。
- 分支机构地图旁边或下方必须同步展示分支机构明细表，至少包含分支机构名称、状态、成立时间和所在地区，保证读者可对照核验。
- 地图 tooltip 必须处理未命中业务数据的地区；不得直接使用 `{c}` 导致无数据省份显示 `NaN`，应显示“暂无数据”或业务口径一致的 0 值说明。
- 地图容器变高后仍要放大地图本体，但不得裁切地图边界；ECharts `map` series 建议设置 `layoutCenter: ['50%', '54%']`、`layoutSize: '105%'`，避免画布留白很大、地图图形偏小、位置偏右或顶部/底部被裁切。
- 地图默认开启 `roam: true`，支持缩放和拖拽；只有明确的 CRM 容器交互限制时才关闭，并在自检中说明。
- `visualMap.max` 应按当前地图数据最大值动态设置，不得写死到明显压低色差或夸大色差的值。
- 地图边界线、南海诸岛 inset、九段线和外轮廓线在浅色底图上必须保持可见性；`itemStyle.borderColor` 建议 `#94a3b8`，`borderWidth` 建议 `0.8-1`，`emphasis.itemStyle.borderColor` 可用 `#64748b`。不要用接近白色的描边，也不要用空白 `graphic` 方框模拟南海诸岛。
- `scatter` / `effectScatter` 只能作为总部、工厂、项目城市的补充点位层，不能单独替代区域着色图。
- 只有灰色底图、空 canvas、地图轮廓或圆点图层时，不得判定为区域分布地图成功。
- 地图失败时退回省份排行、区域分组卡或 fallback table，并记录降级原因。

关键地图配置形态：

```js
echarts.registerMap('china', geoJson)
chart.setOption({
  visualMap: { min: 0, max: maxValue },
  series: [{
    type: 'map',
    map: 'china',
    roam: true,
    layoutCenter: ['50%', '54%'],
    layoutSize: '105%',
    itemStyle: {
      borderColor: '#94a3b8',
      borderWidth: 1
    },
    emphasis: {
      itemStyle: { borderColor: '#64748b' }
    },
    data: [
      { name: '浙江省', value: 1 },
      { name: '安徽省', value: 3 }
    ]
  }]
})
```

## 色彩和视觉边界

- 主色用于目标客户、核心指标、目录高亮和中性重点。
- 尽调报告默认使用清爽企业蓝、科技蓝或深蓝到亮蓝的渐变作为主视觉方向；允许按客户行业微调，但避免大面积黑青、墨绿、脏灰、过暗渐变或沉闷底色。
- 正文页面背景使用白色或极浅冷灰，正文内容区保持白底、干净、可打印；不要让页面整体呈现暗色、灰脏或低对比。
- 封面渐变可从深蓝过渡到中亮蓝，末端可带少量亮蓝增强科技感；不要把封面做成偏黑、偏绿或与正文同质的普通信息卡。
- 绿色用于正向或正常经营；琥珀用于关注或不确定；红色只用于明确风险；灰色用于背景或中性项。
- 财务图表按指标含义着色，不按金额大小简单着色。
- 推荐使用封面标签、状态标签、风险标签、资质标签和信号标签增强扫描效率；标签内容必须来自事实、结构化字段或明确模型归纳。
- 允许少量 emoji / Unicode 图标提升扫描效率，优先用于报告日期、总部、行业、荣誉资质、CRM 状态、风险等级等高频标签；不得替代事实说明，也不要每段滥用。
- 封面可使用深色或渐变；正文避免大面积深色、复杂动画、外部字体和不可控外部图片。
- 不要把封面机械固定为“固定 4 个标签 + 固定一行副标题 + 固定同构卡片”的唯一骨架；允许模型在同一视觉边界内为不同客户选择不同首屏构图。

标签来源映射：

- 荣誉/资质标签优先来自 `basicProfile.qualifications`，其上游应为 `sharecrm intelligence company conc` 的 `honorinfo`、`tbcertificateintegrateinfo`、企业官网、公告、监管/协会名单等可追溯证据；不得仅凭行业、规模或模型印象生成“高新技术企业”“专精特新”“单项冠军”等荣誉标签。
- 行业/业务标签来自 `meta.targetCompany.industry`、`basicProfile.industry`、`businessModel.mainBusinesses`、`businessModel.productsOrServices` 或 `industryContext`；模型归纳出的行业位置或业务特征必须能回链依据。
- 上市、登记状态、总部、注册资本、成立时间等主体标签来自工商基础信息、上市公司简介或已确认公开证据。
- CRM 状态、合作状态、客户阶段等内部标签来自 `crmContext` 和 CRM 对象描述后的业务字段；不得把未查到 CRM 记录写成已建档、已合作或明确阶段。
- 风险标签来自 `riskProfile`、风险类 CLI 或公开司法/监管证据；不得把一般关注点写成明确风险事实。
- 机会、壁垒、关键依赖、卖方相关信号等判断标签来自 `sellerRelevantSignals`、专题归并字段或明确模型归纳，并在正文或图例中保留归纳口径。

## 禁止展示

- 卖方画像原文、卖方产品清单、能力说明或销售卖点。
- CLI 路径、SQL、CRM 对象 API 名、字段 API 名、记录 ID、内部查询参数。
- 联系人手机号、邮箱、身份证等个人敏感信息。
- 内部备注、审批意见、成本、折扣、底价、合同条款、订单明细等敏感商业信息。
- 销售话术、触达路径、跟进节奏、作战计划或自动创建商机/线索建议。
- 证券投资建议、估值判断、股价判断或买卖建议。

## 交付前自检

生成 HTML 后必须做展示完整性自检：

- 是否已读取本文件；未读取不得生成正式 HTML 或宣称自检通过。
- 目录是否只包含实际渲染章节，锚点跳转是否有效，sticky 目录是否遮挡正文。
- 封面、目录、正文左右边界是否一致。
- 封面是否是顶部第一视觉层，目录内容与正文是否对齐，正文底色是否干净。
- 摘要 4 卡是否为 2x2，窄屏是否单列。
- 图表容器是否有稳定高度，数据字段、legend、坐标轴、节点/边关系和 fallback 是否一致。
- 地图是否加载/注册地图数据，是否存在区域着色 `map` series，业务地区是否命中并着色。
- 是否没有空白图表、无效锚点、脚本报错后不可读区域。
- 图表无法稳定渲染时，是否改为表格、列表、时间轴、关系卡、矩阵或文字摘要表达同一数据。
- 每个一级章节是否都具备开头概述结论和末尾业务含义总结。
- 每个真实图表下方是否都有对应详细表格，而不是只有 fallback table。
- 自检只修复呈现问题，不新增客户事实，不改变原有判断。
