# 客户尽调报告输出契约

本文定义 `account-due-diligence-report` 的最终输出契约。它是主报告 Skill 的输出总入口，约束文字版报告和 HTML 报告如何消费同一份中间数据模型、如何裁剪章节、如何展示证据，以及哪些内容不得输出。

具体文字章节结构见 `references/report-template.md`；HTML 展示形态见 `references/html-report-template.md`；数据字段以 `references/schemas/report-data-model.md` 为准。

## 1. 输出形态

默认交付方式为：先输出文字业务概要结论，同时交付一份 HTML 客户尽调报告作为正式完整结果。

在以下场景，HTML 报告视为优先交付形态：

- CRM 详情页、iframe、富文本或浏览器预览需要正式展示。
- 用户明确要求 HTML、页面展示、打印或转 PDF。
- 运行环境支持生成本地 HTML 文件。

若用户未明确要求完整 Markdown/文字长文，不生成完整 Markdown 报告；Markdown 仅在用户明确要求时作为补充交付。

正式结果返回前，先输出导读式文字业务概要结论，提示用户查看完整 HTML 报告；不得在已交付 HTML 报告的情况下，再把整份 Markdown 长文重复输出到最终回复中。

文字版和 HTML 版必须消费同一份 `schemas/report-data-model.md`，不得各自取数、各自推断或各自补写事实。

## 2. 数据消费顺序

正式报告必须按以下顺序生成：

1. 完成目标企业主体锚定。
2. 形成 `schemas/report-data-model.md` 定义的结构化中间数据。
3. 将专题 Skill 编排结果归并到 `industryContext`、`chainContext`、`cooperationContext` 等主报告消费字段。
4. 按本输出契约裁剪章节。
5. 按 `report-template.md` 渲染文字版。
6. 需要 HTML 时，必须先读取并遵守 `html-report-template.md`，再渲染 HTML 版。

报告模板只能消费中间数据模型中的已有字段，不直接拼接原始 CLI 返回、网页全文、CRM 原始记录或专题 Skill 的完整独立报告。

`output-contract.md` 只定义输出契约，不能替代 `html-report-template.md`。已读取 `report-template.md` 或本文件，不等于已读取 HTML 展示规范；未读取 `html-report-template.md` 时不得生成正式 HTML，也不得宣称 HTML 自检通过。

## 3. 标准章节

客户尽调报告通常包含以下章节，但不是固定必出清单：

1. 客户概览摘要
2. 客户主体与基础信息
3. 集团、股权与组织关系
4. 主营业务与商业模式
5. 研发与知识产权实力
6. 行业环境与客户位置
7. 产业链与生态关系
8. 经营动态与业务重点
9. 上市主体公开财务与经营摘要
10. 合作历史与供应商关系
11. 风险与准入信息
12. 与发问方业务相关的情报信号
13. 证据来源

章节是否输出由数据模型中的有效内容决定。不得为了模板完整强行输出“暂无”“未获取到”“待核实”。

## 4. 章节与数据模型映射

| 报告章节 | 主要消费字段 |
|:---|:---|
| 客户概览摘要 | `basicProfile`、`businessModel`、`ipProfile`、`industryContext`、`chainContext`、`cooperationContext`、`riskProfile`、`sellerRelevantSignals` |
| 客户主体与基础信息 | `meta.targetCompany`、`basicProfile` |
| 集团、股权与组织关系 | `ownership` |
| 主营业务与商业模式 | `businessModel` |
| 研发与知识产权实力 | `ipProfile` |
| 行业环境与客户位置 | `industryContext` |
| 产业链与生态关系 | `chainContext` |
| 经营动态与业务重点 | `operationDynamics` |
| 上市主体公开财务与经营摘要 | `publicCompanyFinancials` |
| 合作历史与供应商关系 | `cooperationContext`、`cooperationHistory` |
| 风险与准入信息 | `riskProfile` |
| 与发问方业务相关的情报信号 | `sellerRelevantSignals` |
| 证据来源 | `evidence` |

`topicInsights` 只用于追溯专题 Skill 在编排调用模式下返回了什么，不作为正式报告的主要渲染入口。

## 5. 输出写法要求

- 每个章节按“开头概述结论 -> 明细内容 -> 末尾业务含义总结”组织；详细写法仍保持“事实是什么 -> 说明客户什么情况 -> 对业务理解有什么影响”。
- 客户主体、业务、行业、产业链、合作和风险信息必须围绕目标客户解释，不写成通用资料汇编。
- 研发与知识产权实力只基于专利、软著、标准、商标、ICP备案及可追溯公开证据解释技术资产和产品支撑；知识产权出质应归入风险或融资补充，不写成研发实力。
- 知识产权出质和股权出质必须分开表达：知识产权出质来自 `risk conc:intellectualinfo`，股权出质来自 `risk conc:pledgeinfo`；没有数据时分别说明或动态裁剪，不得用“无股权出质记录”代替知识产权出质结论。
- 行业内容只输出与目标客户相关的行业摘要、客户位置和客户影响，不输出完整行业市场报告。
- 产业链内容只输出客户相关的上下游、渠道、生态、关键依赖和业务含义，不输出全行业产业链图谱。
- 合作历史不能只列新闻，必须说明合作对象类型、合作性质和关系含义。
- 风险信息不能只列记录，必须说明风险性质、时间、状态和业务影响。
- 与发问方业务相关的情报信号只说明客户侧事实为什么相关，不输出具体销售动作。
- HTML 报告必须包含悬浮目录和来自 `schemas/report-data-model.md` 的 `visuals` 或结构化字段生成的可视化模块；文字版报告不强制图表。正式 HTML 通常应包含 2-4 个高信息密度可视化，数据不足时至少 1 个。
- 不得为了可视化编造客户事实、金额、份额、排名或风险记录；允许把已获证据做定性归纳并可视化，但必须标注归纳口径，且图表、时间轴、关系卡片与正文、表格保持一致。
- 图表必须服务具体业务问题，优先嵌入对应业务章节。不得把低价值图表集中堆在“关键结构可视化”章节里凑数量；不得用专题调用覆盖率、无证据评分、伪占比或伪趋势替代真正的客户理解。
- 每个一级章节都必须有开头概述结论和末尾业务含义总结；不得只有图表和资料堆叠，没有章节判断落点。
- 每个真实图表下方必须附对应详细表格，或在同章节紧邻展示可核验表格。这里的真实图表包括地图、柱状图、折线图、趋势图、Sankey、关系网络图、热力图、矩阵图和构成图；KPI 卡、摘要卡、标签组和信号卡不强制单独配表，但所在章节仍必须有明细表支撑。

## 6. 证据展示规则

- 关键事实、判断和推断必须通过 `evidenceRefs` 回链顶层 `evidence`。
- 证据来源只展示业务可读的来源名称、时间和支撑内容。
- 内部追溯字段只留在 `evidence.internalTrace`，不得进入报告正文或 HTML 展示。
- CLI 返回为空、CRM 查询为空或公开来源无证据时，不得直接写成“该事项不存在”。
- 取数覆盖范围只在影响关键判断时展示，不作为报告开头固定章节。
- `total`、首批返回数和当前有效数量必须分开；首批样本不能写成全量事实。若列表未全量返回，正文只在影响判断时用自然语言说明“明细未完整返回，不做全量判断”，不要把内部字段名生硬写进正文。
- CRM 名称归一未精确命中、仅返回模糊候选或别名冲突未解决时，不得把内部记录写成已确认 CRM 覆盖事实；CRM 状态卡、内部合作状态和内部摘要章节应动态裁剪或明确降级。

## 7. 角色与场景裁剪

报告必须结合 `meta.userContext` 和 `role-output-rules.md` 做轻量裁剪：

- 销售：突出客户是谁、做什么、合作关系、供应商/竞品和相关情报信号。
- 销售管理者：突出客户价值、风险、合作复杂度和业务判断依据。
- 售前：突出客户业务模式、场景复杂度、产业链关系和系统相关信号。
- 客户成功：突出历史合作、合同/订单、回款、经营压力和续费/扩容背景。
- 风控/签约：突出主体有效性、股权关系、风险记录、履约能力和账期风险。

角色裁剪只能改变重点和篇幅，不得改变事实、证据或边界。

## 8. HTML 输出契约

HTML 报告是文字版报告的展示形态，不是另一套分析逻辑。

HTML 输出必须遵守：

- 章节与文字版保持一致，并按有效数据动态裁剪。
- 必须包含悬浮目录、章节锚点和滚动高亮；目录只包含实际渲染章节。
- 必须包含可视化模块；优先消费 `visuals`，或由 `ownership`、`businessModel`、`ipProfile`、`industryContext`、`chainContext`、`operationDynamics`、`cooperationHistory`、`riskProfile`、`publicCompanyFinancials`、`sellerRelevantSignals` 等结构化字段生成股权结构、产品-场景覆盖、知识产权结构、产业链关系、动态时间轴、合作事件、招投标趋势、财务期间表、风险矩阵或客户侧情报信号矩阵。
- `topicInsights` 只能用于追溯专题结果和辅助摘要，不应单独生成“专题覆盖饼图”等低业务价值图表。
- 不新增文字版没有依据的客户事实、CRM 记录、风险记录、合作关系或卖方判断。
- 可使用少量 JavaScript 做目录高亮和图表渲染，但只能消费当前数据模型中的已有字段，不得异步拉取新数据、补充新事实或改写结论。
- 在支持受信任脚本依赖的场景，可优先使用 ECharts 作为可视化方式；如环境不支持或图表不稳定，应退回 CSS 时间轴、关系卡片、矩阵、表格增强或摘要块，不能输出无可视化的纯文本 HTML。
- 每个可视化必须有 fallback table 或文字结论；数据不足时输出可视摘要块或表格，不输出空白图表容器。
- 每个真实图表在正常渲染成功时也必须有详细表格，不得把详细表格仅作为脚本失败时的 fallback 方案保留。
- 区域分布存在省份/城市字段时，HTML 必须按 `html-report-template.md` 的地图硬规则优先输出区域着色图；未生成时必须在 `visuals[].mapConfig.downgradeReason` 或 `coverageNote` 记录原因，不能只用圆点图、表格或柱状图静默替代。
- 允许使用热力图、Sankey、关系网络图、雷达图、树图、漏斗图、组合图等表达复杂关系；只要节点、边、类别或等级能回链证据或明确标注为模型归纳即可。
- 颜色必须有稳定语义：主色用于核心主体和中性重点，绿色用于正向/健康，琥珀用于关注/不确定/成本压力，红色用于风险，灰色用于背景或中性项。财务图表不得仅按金额大小上色，应按指标含义上色。
- 封面、摘要区、业务卡片和信号区允许使用受控 emoji / Unicode 图标，提升扫描效率；不得用图标替代事实说明。
- 使用内联 CSS，适合 CRM 页面、浏览器预览、打印和转 PDF。
- HTML 文件名必须使用 `客户尽调报告-<企业简称或工商全称>-<YYYYMMDD>.html`，不得使用临时调试名、版本后缀或下划线自定义命名。
- 不展示技术追溯字段、CRM 对象 API 名、记录 ID、CLI 路径或内部查询参数。
- 最终回复在已交付 HTML 报告时，应只输出业务概要结论和“可查看完整报告”的提示，不重复整份正文。

## 9. 禁止输出

主报告不得输出：

- 销售触达路径、销售话术、跟进节奏、作战计划、谈判策略。
- 推荐联系谁、推荐推什么产品、自动创建线索或商机。
- 卖方画像原文、卖方产品清单、能力说明或销售卖点。
- CRM 对象 API 名、字段 API 名、内部记录 ID、敏感字段原值。
- 联系人手机号、邮箱、身份证等个人敏感信息。
- 内部备注、审批意见、成本、折扣、底价、合同条款和订单明细等敏感商业信息。
- 证券投资建议、估值判断、股价判断或买卖建议。
- 没有证据支撑的合作关系、供应商关系、竞品占位、风险结论或客户需求判断。

## 10. 降级输出

| 情况 | 输出处理 |
|:---|:---|
| 主体无法唯一确认 | 不生成完整报告，返回候选主体让用户确认 |
| 卖方画像缺失 | 输出客户事实，不做强相关性判断，不固定输出缺失说明 |
| CRM 不可用或权限不足 | 使用企业情报和公开来源，内部记录相关章节动态裁剪 |
| 专题 Skill 未调用或无有效结果 | 继续生成主报告，但必须记录未调用/无有效结果原因；不固定输出对应章节的空占位 |
| 风险、合作或产业链证据不足 | 不输出强判断，必要时在相关章节保留简短待核实说明 |
| HTML 文件生成不可用 | 默认仍返回完整 HTML 内容或说明生成失败原因；只有用户明确要求 Markdown/文字版时才改为 Markdown/文字交付 |

## 11. 输出前自检

正式输出前必须按 `quality-checklist.md` 自检。自检结果不得作为报告章节输出。
