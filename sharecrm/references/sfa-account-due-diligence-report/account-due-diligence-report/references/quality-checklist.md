# 质量自检清单

本清单仅供内部验证，不得作为报告章节输出。

## 主体与流程

- [ ] 目标企业主体是否已通过工商全称或用户确认消歧。
- [ ] 用户输入为简称、品牌名、产品名、股票简称或非完整工商名称时，是否先调用 `sharecrm intelligence company search` 做结构化候选召回，而不是先进入 web search 或反复试错多个企业信息 CLI。
- [ ] `company search` 返回多候选或主体冲突时，是否返回前 3-5 个候选让用户确认，没有直接套用名称相近主体。
- [ ] 用户输入为简称、品牌名或股票简称时，是否使用股票代码、信用代码、官网、行业/业务关键词、上市身份等辅助锚点核对；若命中主体与上下文冲突，是否已补查候选或要求确认。
- [ ] `meta.targetCompany.entityResolution` 是否记录主体确认依据、候选主体和冲突处理。
- [ ] 后续企业情报查询是否使用统一工商全称。
- [ ] 卖方画像是否优先调用系统配置 CLI 读取 `service_models`。
- [ ] `service_models` 缺失时，是否只使用明确上下文或 CRM 产品/已成交摘要作为内部推理降级来源。
- [ ] CRM 查询是否先识别对象、获取对象描述，再基于字段 label 和类型解释业务含义。
- [ ] CRM 是否默认只查询预设对象，没有全量扫描自定义对象。
- [ ] CRM 名称归一未精确命中时，是否没有把模糊候选误写为已确认客户记录；如使用别名或历史名称命中，是否记录了确认依据。
- [ ] 卖方画像是否只参与推理，没有原样展示。
- [ ] 是否没有默认卖方行业。
- [ ] 专题 Skill 结果是否被裁剪为客户报告需要的摘要。
- [ ] 客户尽调正式报告是否默认编排调用行业分析、产业链分析、合作历史三个专题 Skill；未调用时是否记录明确原因。
- [ ] 专题 Skill 编排前是否已读取 `references/skill-composition.md`，并按其中 `minimumReferenceSet` 执行专题 references 深读。
- [ ] 已调用专题 Skill 是否读取了各自的 `references/enterprise-cli-map.md`；涉及企业情报、公开动态、招投标、合作事件、上市公告或外部证据时，是否没有只读专题 `SKILL.md` 就返回结论。
- [ ] 每个已调用专题 Skill 是否在 `topicInsights.<topic>.referenceReadStatus` 记录 `required/read/missing/status/downgradeReason`。
- [ ] 如果某专题只读取了 `SKILL.md`，是否将该专题标记为 `partial`，且没有宣称专题编排完整通过。
- [ ] 若任何专题 `referenceReadStatus.status=partial | failed`，最终自检是否未标记“专题编排全部通过”，并在报告或日志中说明降级原因。

## 数据与证据

- [ ] 工商、股权、风险、上市等企业情报是否优先走内部 CLI map。
- [ ] `sharecrm intelligence company conc` / `risk conc` / `ip conc` 是否只传入 `enterprise-cli-map.md` 白名单内的 `actionTypes`，没有一次性传入全部支持类型。
- [ ] 知识产权与研发实力是否使用 `ip conc` 的专利、软著、标准、商标、ICP备案等数据承接，并与知识产权出质风险分开解释。
- [ ] 新闻、公开动态或舆情提及如使用 `sharecrm intelligence market search-mentions`，是否按 `search-mentions-cli.md` 校验 `keyword`、时间窗、来源、分页、排序、匹配字段、情感、站点、用户和地域参数。
- [ ] `search-mentions` 是否没有把超过 7 天的窗口一次性发送；更长口径是否按不超过 7 天的窗口分段查询并记录覆盖范围。
- [ ] `search-mentions` 返回字段是否按实际响应兼容处理，例如 `gtime` 只能作为采集时间，`total` 不直接当作全库总命中量。
- [ ] 新闻类 CLI、`search-mentions`、公告、公开 web 来源等多来源动态是否在输出前按标题、链接、来源、时间和内容相似度去重，没有重复展示同一事件。
- [ ] CLI 空、失败或字段不足时，是否继续通过公开 web 来源补查。
- [ ] web search / web fetch 是否只在 CLI 不可用、返回空、字段不足、需要权威原文补证或用户明确要求时使用；是否没有在失败页面上长时间等待或反复重试。
- [ ] 专题阶段每个主题是否控制在 1-2 个精准 query、每个 query 只消费前 3-5 条高质量结果。
- [ ] 分页类数据是否先确定时间窗、筛选或排序，再获取首批记录。
- [ ] 首批或定向查询的覆盖范围是否写入 `meta.retrievalCoverage`。
- [ ] 列表型 CLI 是否区分 `returnedCount`、`total`、`isLastPage` 和状态字段；是否没有把 `total` 写成有效数量或全量结论。
- [ ] 空字段 item、角色不清或状态不可用的记录是否没有进入正式结论和图表。
- [ ] 主体基础字段是否以 `company conc:baseinfo` 为最高优先级；web、百科、新闻是否没有覆盖工商全称、信用代码、成立日期、法定代表人、登记状态和注册资本。
- [ ] 资质/许可是否按状态和类型过滤；食品经营许可、营业执照、特种设备使用登记等是否没有被写成技术能力或行业地位亮点。
- [ ] 知识产权出质、股权出质和研发知识产权资产是否分开表达。
- [ ] 上市财务三表是否先确认上市主体口径；当前 CLI 1.1.8 未验证修复前，是否只传 `companyName`，不传 `reportYear/pageNum/pageSize`。
- [ ] 用户指定年份时，是否先在第一页返回列表中按 `reportYear/endDate/reportDateType/isAudit` 筛选；如未覆盖目标年份，是否记录覆盖不足并改用公开年报、公告或交易所来源补证。
- [ ] 是否没有把第一页缺失写成该年份不存在财报；是否没有在 `--data`、显式 flag、字符串/数字年份之间反复试错。
- [ ] 关键判断是否有证据来源。
- [ ] 模型推断是否与事实区分。
- [ ] 是否没有编造 CRM 记录、合作关系、风险记录或内部案例。
- [ ] 旧资料是否保留时间口径。

## 报告内容

- [ ] 客户概览摘要是否只放已获取到的核心信息。
- [ ] 是否没有固定输出证据缺口或待核实事项。
- [ ] 每个一级章节是否都采用“开头概述结论 -> 明细内容 -> 末尾业务含义总结”的结构，而不是只有资料堆叠。
- [ ] 主营业务是否解释了客户卖什么、卖给谁、怎么卖。
- [ ] 风险信息是否解释了业务影响。
- [ ] 合作历史是否区分了合作对象类型和关系含义。
- [ ] 与发问方相关的情报信号是否基于卖方画像推理。
- [ ] 上市主体财务信息是否只作为经营、预算、履约和风险背景，没有写成证券投资判断。

## 边界

- [ ] 是否没有输出触达路径、销售话术、跟进节奏或作战计划。
- [ ] 是否没有输出最终商机推荐或资源投入决策。
- [ ] 是否没有输出证券投资建议。
- [ ] 是否没有展示卖方产品/订单/合同敏感明细。

## HTML / 交付

- [ ] 需要 HTML 时，本轮是否已经读取 `references/html-report-template.md`；如未读取，HTML 自检必须失败，不能生成正式 HTML 或宣称自检通过。
- [ ] 正式交付是否默认采用“先输出文字业务概要结论 + HTML 完整报告”；如用户未明确要求完整 Markdown，是否没有把整份 Markdown 长文重复输出到最终回复中。
- [ ] `output-contract.md`、`report-template.md` 是否没有被误当作 HTML 模板替代品。
- [ ] HTML 文件名是否为 `客户尽调报告-<企业简称或工商全称>-<YYYYMMDD>.html`，没有使用临时调试名、`v2` 后缀或下划线自定义命名。
- [ ] HTML 是否按 `references/html-report-template.md` 的展示规范生成，而不是临时拼接页面，也不是机械照抄默认代码示例。
- [ ] 长 HTML 是否包含实际渲染章节的悬浮目录、锚点和滚动高亮规则。
- [ ] 悬浮目录是否使用 `position: sticky` 或等效实现，且目录项只包含实际渲染章节。
- [ ] 目录是否优先采用封面下方横向 sticky 样式；若使用深色侧栏，是否确有长目录或标题拥挤原因，且没有让大面积深色压过正文。
- [ ] 横向目录版式下，封面、目录和正文 main 是否共享同一外层宽度；是否没有给 `.report`、`main` 或正文外层设置比 `.shell` 更窄的 `max-width`，导致正文左右留白大于顶部。
- [ ] 封面是否优先作为顶部贯通第一视觉层，而不是被包成普通圆角卡片；若封面内容不全宽，封面内容、目录内容和正文是否仍保持左右对齐。
- [ ] 首屏是否形成“封面 + KPI/摘要卡 + 高价值可视模块”的完整阅读节奏，而不是只有标题和长段文字。
- [ ] HTML 是否包含来自数据模型的可视化模块；结构化信息充足时是否生成 2-4 个高信息密度图表或可视摘要，而不是只输出一个保守图表。
- [ ] HTML 可视化是否优先消费 `visuals` 或数据模型结构化字段；是否没有临时从正文编造图表数据。
- [ ] 每个可视化是否有 fallback table 或文字结论，避免脚本不可用时不可读。
- [ ] 每个真实图表下方是否都有对应详细表格，而不是只有脚本失败时才出现 fallback table。
- [ ] KPI 卡、摘要卡、标签组和信号卡如未单独配表，所在章节是否仍有明细表支撑。
- [ ] 图表容器是否按类型设置稳定尺寸；地图桌面端是否不低于 `560px` 且建议约 `580-620px`，Sankey/关系网络是否约 `500-640px`，热力图/矩阵是否约 `440-500px`；是否没有让地图、Sankey、热力图复用 360-380px 的通用高度。
- [ ] 概览摘要若有 4 张结论卡，桌面端是否为 2x2 或等效均衡布局，窄屏是否单列；是否避免 `auto-fit + minmax` 造成常见宽度下 3+1；是否没有固定卡片高度导致溢出或大空白。
- [ ] 是否允许并合理使用热力图、Sankey、关系网络图、组合图、雷达图、矩阵图等更适合当前数据的问题表达。
- [ ] 行业章节结构化信息充足时，是否优先尝试热力图/矩阵图；产业链关系存在方向性时，是否优先尝试 Sankey/分层流向图。
- [ ] 股东分布是否默认优先使用环形图/饼图；比例不完整时是否明确“已披露股东/投资方构成”口径，股东较多或名称较长时是否合并小项并配明细表。
- [ ] 行业分布、行业事件类型、竞争格局或公开动态来源构成是否按数据特点选择热力图、定性矩阵、分组条形图、趋势组合图或环形图/饼图；是否没有把判断类信息做成伪占比饼图。
- [ ] 行业章节在结构化信息充足时，是否至少输出一个行业图表；若降级为纯表格，是否确有证据不足、样本过少或维度不清原因。
- [ ] Sankey 是否只在存在方向关系时使用；节点和边是否能回链结构化字段、证据或明确模型归纳；没有真实金额/次数/数量时，布局值是否明确标注不代表真实流量、份额或金额。
- [ ] 热力图/矩阵是否有清晰二维维度和可读标签；定性等级是否展示等级含义并标注归纳口径，没有伪装成真实评分、排名或市场份额。
- [ ] 区域分布有省份/城市、登记机关、地址或名称可推导地域字段时，是否按 HTML 地图硬规则优先尝试区域着色图；未使用地图时是否记录降级原因。
- [ ] ECharts 地图是否已加载/注册地图数据，记录 `mapDataUrl`，且默认优先使用公司内部地区边界地址 `https://a9.fspage.com/FSR/weex/sfa/resource/map_boundary.json`；`mapName`、`series.map`、地区名称口径是否一致。
- [ ] 地图是否包含 `series.type='map'` 区域着色层并命中业务地区；圆点层是否仅作补充，没有被误判为区域分布地图成功。
- [ ] 分支机构地图若已渲染，`value` 是否为按省级行政区聚合后的分支机构数量，而不是仅表达“是否覆盖”；总量 100 家以内时是否已取全量明细，tooltip 是否明确显示数量口径。
- [ ] 分支机构是否没有使用状态饼图、类型饼图或注销/存续占比图替代区域地图；地图无法稳定渲染时是否降级为省份排行、区域分组表或明细表。
- [ ] 分支机构地图旁边或下方是否同步展示了分支机构明细表，至少包含名称、状态、成立时间和所在地区，便于读者对照核验。
- [ ] 地图 tooltip 是否处理未命中业务数据的地区，没有让无数据省份显示 `NaN`、`undefined` 或与业务口径不一致的数值。
- [ ] 地图图形是否充分利用容器空间；是否设置了合适的 `layoutCenter: ['50%', '54%']` / `layoutSize: '105%'` 或等效配置，避免地图本体明显偏小、四周留白过大、位置偏右或边界被裁切。
- [ ] 地图是否默认开启 `roam: true` 以支持缩放和拖拽；如关闭是否有明确容器限制原因。
- [ ] `visualMap.max` 是否按地图数据最大值动态设置，没有写死导致颜色不显著或失真。
- [ ] 南海诸岛 inset、九段线和外轮廓线在浅色底图上是否保持清晰可见；边界线是否使用类似 `#94a3b8` 的灰色描边，没有使用过浅描边或空白 `graphic` 方框模拟南海诸岛。
- [ ] 城市级地区是否已归一为地图数据使用的省级/直辖市/自治区/特别行政区完整名称，并记录 `matchedRegions`、`unmatchedRegions` 或明确降级原因。
- [ ] 定性归纳型可视化是否标注了模型归纳口径，没有把强/中/弱、高/中/低、已证实/推断/待核实伪装成原始统计值。
- [ ] 是否没有为了凑图表数量生成“专题覆盖饼图”、无证据雷达评分、伪占比、伪趋势或其他低业务价值图表。
- [ ] 图表是否嵌入对应业务章节，如股权图在组织章节、产业链图在产业链章节、财务图在财务章节，而不是集中堆在一个“关键结构可视化”章节里。
- [ ] 颜色是否有稳定语义；财务图是否按指标含义着色，而不是按金额大小着色。
- [ ] 主视觉是否使用清爽企业蓝/科技蓝或相近专业色调；是否避免黑青、墨绿、脏灰、过暗渐变、大面积暗色底或低对比底色。
- [ ] 正文页面背景是否为白色或极浅冷灰，内容区是否保持白底、干净、可打印，没有让整体报告显得灰脏或沉闷。
- [ ] 封面是否与普通正文 section 明显区分；是否没有被白底卡片样式降级成普通内容块。
- [ ] 封面是否没有被机械固定成唯一骨架，例如固定标签数量、固定副标题句式或完全同构的首屏卡片布局。
- [ ] 正文是否像正式报告而不是表单：没有把所有 section 都做成同质边框卡片，没有过度压缩留白、字号和图表高度。
- [ ] 封面标签、状态标签、风险标签、资质标签和信号标签是否来自事实、结构化字段或明确模型归纳，没有编造荣誉、状态或判断。

- [ ] 每个图表是否回答了一个明确问题，且比表格、列表或摘要更易理解。

- [ ] HTML 交付前是否完成展示完整性自检，并修复空白图表、无效锚点、目录遮挡、脚本配置错误或其他明显渲染异常；如图表无法稳定渲染，是否改为表格、列表、时间线、关系卡、矩阵或文字摘要表达同一数据。
- [ ] ECharts 或其他受信任脚本依赖不可用时，是否仍有可读的无图表降级表达。
- [ ] 地图依赖加载失败、地图注册失败或地区名称无法匹配时，是否没有留下空白地图容器，而是展示省份排行、区域分组或表格 fallback。
