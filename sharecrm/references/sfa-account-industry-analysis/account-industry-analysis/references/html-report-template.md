# HTML 客户行业分析模板

本文定义 `account-industry-analysis` 的 HTML 输出形态。最终输出边界、数据消费顺序、章节裁剪和证据展示规则以 `output-contract.md` 为准；本模板只负责 HTML 展示结构。HTML 结果用于 CRM 页面展示、浏览器预览、打印或转 PDF，内容必须消费同一份 `schemas/standalone-report-data-model.md`，不得新增文字版结果没有依据的事实。

## 输出原则

- HTML 结果是正式展示形态，不是另一套分析逻辑。
- HTML 章节与 `output-contract.md` 的独立输出模板保持一致，并根据已有信息动态裁剪。
- 使用完整 HTML 文档结构和内联 CSS，避免外部依赖。
- 可使用少量内联 JavaScript 仅做目录锚点高亮和滚动跟随，不得异步加载、改写或补充报告内容。
- 样式应偏正式业务分析，适合 CRM iframe、富文本预览、浏览器打开和打印。
- 可打印、可转 PDF，避免依赖屏幕交互才能理解内容。
- 每个一级章节必须包含：开头概述结论、明细内容、末尾业务含义总结。

## 内容一致性

HTML 结果必须与文字版共享：

- 同一份目标客户主体。
- 同一份 `industryContext`、`sellerRelevantSignals`、`gaps` 和 `evidence`。
- 同一份 `meta.retrievalCoverage` 覆盖范围说明。
- 同一套事实 / 推断 / 待核实边界。
- 同一套脱敏和禁止展示规则。

HTML 可以用摘要块、表格和证据标签提升可读性，但不能额外编造客户事实、内部样本、卖方画像、行业事件或政策结论。

## 标签来源规则

- HTML 中的标签、徽章和 emoji 文案必须来自 `schemas/standalone-report-data-model.md` 中已有字段、`industryContext`、`crmContext`、`sellerRelevantSignals`、`gaps` 或可回链 `evidence` 的事实/归纳。
- 行业分类、行业阶段、客户行业位置、趋势、政策、风险和机会标签分别来自 `industryContext`、CRM 行业锚点、企业情报 CLI、公开政策/公告/新闻或明确模型归纳；不得把泛行业描述写成已证实的客户行业地位。
- 荣誉/资质标签仅在主报告传入的资质字段、企业情报 CLI 结果或公开证据明确支持时展示；不得仅凭行业分类、客户规模、融资或技术描述生成“高新技术企业”“专精特新”“单项冠军”等标签。
- 模型归纳标签必须能回链行业判断依据、客户事实、CRM/公开证据或 `sellerRelevantSignals`，并在正文或图例保留归纳口径。

## 视觉表达自由度

不要把 HTML 结果限制成纯白卡片和普通表格。允许模型根据客户行业、行业阶段和信息密度自由选择更有解释力的视觉表达：

- 封面可以使用品牌色、行业感配色、渐变背景、浅纹理或几何层次，并与正文 section 明显区分。可使用深色封面，但避免深色封面和深色全高目录同时占据过大面积。
- 封面可采用通栏背景 + 限宽内容，也可采用受控限宽封面；不固定标签数量、KPI 数量、摘要卡样式或副标题句式，只要求首屏有明确层次和视觉重点。
- 允许使用 emoji 或 Unicode 图标作为轻量视觉锚点，用于目录标题、行业结论、趋势卡片、政策标签、风险/机会信号和图表标题。
- 当存在产品/服务、应用场景、行业趋势、客户匹配度、机会强弱或影响程度等结构化字段时，优先尝试热力图或矩阵图表达“场景 x 影响/机会/匹配度”；不适合热力图时，再使用雷达图、趋势组合图、关系图、树图或指标卡。
- 允许将强/中/弱、高/中/低、已证实/推断/待核实等模型归纳可视化，但必须标注归纳口径，不得伪装成原始统计值。

边界：不为视觉效果发明行业规模、份额、排名、客户事实、CRM 记录或卖方信息。

行业章节图表下限：

- 行业专题只要结构化信息充足，至少输出一个行业图表；不得在整份报告已有其他图表的情况下，把行业专题长期降级为只有文字和表格。
- 可视化优先顺序：行业变化影响与产品/场景匹配优先热力图或定性矩阵；竞争格局优先分组条形图、雷达图或关系图；行业事件类型、公开动态来源构成等真实构成信息可用分组条形图、趋势组合图或环形图/饼图。
- 只有证据不足、维度不清或样本过少时，行业章节才允许退回纯表格表达，并在正文中保留降级说明。
- 每个真实图表下方都必须附对应详细表格；不得把详细表格仅作为 fallback 保留。
- 首屏应优先形成“封面 + 行业结论摘要 + 至少一个行业高价值图表或矩阵 + 对应明细表”的组合，而不是只放长段行业背景。

## 图表尺寸与热力图规则

- 不要让热力图、矩阵图和趋势组合图复用普通图表的 360-380px 高度。普通图表建议 `min-height: 360px`；热力图/矩阵图桌面端建议 `min-height: 460px`，行列标签较多时提高到 `500px`；移动端不得低于 `400px`。
- 图表初始化前容器必须已有稳定宽高；窗口尺寸变化时调用 `chart.resize()`。
- 热力图必须回答“哪些产品/能力匹配哪些场景、趋势或机会更强”。行列维度必须语义清晰，例如“产品/能力 x 应用场景”“业务板块 x 行业趋势”“机会主题 x 证据强度”“行业事件类型 x 影响强弱”“竞争对象 x 对比维度”。
- 真实数量、金额、次数可直接入图；强/中/弱、高/中/低、已证实/推断/待核实等定性等级必须标注为模型归纳，并展示等级含义。
- 不得把模型归纳等级包装成真实评分、市场份额或客观排名。
- 维度少于 2x2、标签过长导致不可读或证据不足时，改用定性矩阵、信号卡或表格增强。热力图必须提供 fallback table，保留行、列、等级/数值和依据说明。
- 行业事件类型、客户业务领域、公开动态来源等真实构成类别少且样本完整时，可用环形图/饼图；行业影响、机会强弱、客户匹配度等判断类信息仍优先热力图/矩阵，不得做成伪占比饼图。

## 长文档目录规则

- HTML 结果应为实际渲染出的章节生成目录；没有渲染的章节不得出现在目录中。
- 桌面端默认优先使用封面下方的横向 sticky 目录，让热力图、矩阵图和表格获得更宽展示空间；章节很多或标题很长时，可改用侧栏 sticky 目录。
- 横向目录宜使用浅色、半透明白或低饱和底色，当前章节用下划线、浅底或细色条高亮；避免默认使用深色全高侧栏。
- 移动端目录优先保持顶部 sticky 横向滚动；必要时可折叠成紧凑目录，不能遮挡正文。
- 目录项点击后跳转到对应 `section id`，正文应设置 `scroll-margin-top`。
- 目录高亮可使用少量内联 JavaScript 或 `IntersectionObserver`，脚本只允许控制目录状态。

  <style>
    /* 使用内联 CSS；样式保持正式、清晰、可打印。 */
  </style>

<body>
  <main class="report">
    <header class="cover">
      <p class="eyebrow">客户行业分析</p>

## 样式规则

- 使用简洁正式但有视觉完成度的版式：清晰标题、紧凑段落、表格、摘要块、图标卡和高信息密度图表。
- 适合 CRM 工作台阅读，不做营销页、海报页或花哨动效。
- 使用 `max-width` 控制正文宽度，打印时移除多余阴影和背景。
- `行业变化对客户的影响` 优先尝试热力图或矩阵图表达影响强弱、机会强弱和客户匹配度；证据不足或维度过少时再使用表格。
- `与发问方业务相关的行业信号` 和 `证据来源` 可用表格、信号卡、矩阵或标签组展示，避免整页只有表格。
- `行业情报结论` 和 `客户行业位置` 优先用摘要块展示。
- 长报告使用悬浮目录 + 正文布局；默认横向 sticky 目录，侧栏目录作为长目录备选。
- 允许封面使用大面积背景色或渐变；正文避免无关装饰、复杂动画、外部字体和不可控外部图片。深色应作为重点视觉层，不应同时覆盖封面和整条目录栏。

## CRM 内嵌展示规则

- 默认宽度按 CRM 内容区适配，推荐正文容器 `min-width` 不超过 960px。
- 可使用侧边或顶部目录辅助长文档阅读，但正文必须在没有交互时仍可顺序阅读。
- 首屏优先展示 `行业情报结论` 和 `客户行业位置`，避免用户进入页面后先看到长背景综述。
- `行业背景摘要` 必须压缩为客户理解相关内容，不在 CRM 内嵌版本展开完整行业研究。
- `meta.retrievalCoverage` 仅在覆盖度会影响结论理解时，以简短提示块展示。
- 每个一级章节开头应先给出概述结论，结尾补业务含义总结；不得只有图表和事实罗列。
- CRM 内嵌版的表格列数要受控，避免横向滚动；必要时把长文本改成分点摘要。

## 章节渲染规则

- 章节只在对应数据存在时渲染。
- 无数据章节不输出占位文案，例如“暂无”“未获取到”“待核实”。
- `待核实事项` 只在确实存在、且会影响关键判断时渲染。
- `证据来源` 只展示业务可读来源名称、时间和支撑内容。
- 同一条证据可以被多个判断引用，但在证据区只出现一次。

## 脱敏和禁止展示

HTML 结果不得展示：

- 卖方画像原文、配置 CLI 原始返回值、卖方产品清单或能力说明。
- CLI 路径、SQL、对象 API 名、CRM 记录 ID 等技术追溯信息。
- 联系人手机号、邮箱、身份证等个人敏感信息。
- 内部备注、审批意见、成本、折扣、底价、合同条款、订单明细等敏感商业信息。
- 触达路径、销售话术、跟进节奏、作战计划或资源投入建议。

## HTML 交付前自检

- 生成 HTML 结果后，交付前必须做一次展示完整性自检。
- 自检重点包括：目录项是否只对应实际渲染章节、锚点跳转是否有效、sticky 目录是否遮挡正文、表格/摘要块/图标卡/矩阵是否完整。
- 如使用 ECharts、内联 SVG 或 JavaScript 图表，必须检查容器高度、数据字段引用、`series`、`legend`、坐标轴/维度标签和 fallback 内容是否一致。
- 不得保留空白图表容器、无效锚点、脚本报错后不可读的图表区域，或因目录层遮挡导致无法阅读的正文。
- 如图表无法稳定渲染，必须改为表格、列表、信号卡、矩阵或文字摘要表达同一数据。
- 每个一级章节是否都具备开头概述结论和末尾业务含义总结。
- 每个真实图表下方是否都有对应详细表格，而不是只有 fallback table。
- 自检只用于修复 HTML 呈现问题，不新增客户事实，不改变原有判断，不补写没有证据的行业规模、份额或排名。

## 打印和交付

- HTML 文档应可直接保存为 `.html` 文件。
- 文件名必须使用 `客户行业分析-<企业简称或工商全称>-<YYYYMMDD>.html`。
- 打印样式应保证标题、表格和证据来源可读。
- 如果运行环境不能创建 HTML 文件/附件，默认仍返回完整 HTML 内容或说明生成失败原因；只有用户明确要求 Markdown/文字版时才改为 Markdown/文字交付。可以创建文件时，文件对象应作为内部产物或附件卡片返回，不在最终回复正文中打印原始文件对象 JSON、内部路径或 `{"type":"file","path":"..."}`。
