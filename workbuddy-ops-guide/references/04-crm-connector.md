# 04 CRM / 业务系统连接器实操方法论

> 本章是**方法论**，不绑定任何具体平台。
> 具体平台的通道名、对象 API 名请在自己环境里确认后，记到本文件末尾的「本机速查」小节。

## 4.1 ★ 通道要分开记，别一竿子打翻（D01）

**现象**：一条通道挂了，就判定"连接器整体不可用"。

**根因**：一个平台常有多条通道（官方 MCP / 自建 SSE / 直连 API / 代理网关），**各自独立**，故障不联动。

✅ 先用最简单的只读调用探活（如 `get-current-user`），再判断。
**记录时分开写**：哪条可用、哪条失效、失效到什么程度（超时/鉴权错/参数 bug）。

## 4.2 ★ 双名字参数（D02 · 最高频坑）

**现象**：传了对象名，却读不出对象描述。

**根因**：这类工具常需要**两个参数**——一个是"工具执行标识"（固定字符串），一个是"业务对象名"。少传前者就读不出来。

```json
{ "apiName": "GetObjectDescribe",       // 工具执行标识（文档里写的固定值）
  "object_api_name": "<你的对象名>" }   // 业务对象
```

✅ 第一次调用某个工具前，**先查它的参数 schema**，确认是否有这类"双名字"要求。

## 4.3 用"轻量描述"省 context（D03）

对象字段很多时，默认返回会把 context 撑爆。优先选轻量/简化开关（如 `simple_describe=True`），通常只返回字段名、类型、选项、引用目标——**够用且省几倍 token**。

## 4.4 查询结果分页与截断（D04）

- **单页硬上限**很常见（如 50 条）：必须 offset 翻页，直到返回明确标识"未达上限"为止。**"总数≤N"的结论不可信**。
- **长 IN 列表会静默漏数据**：拆成单条查询，或每批少量值。

### D05 导出清单不是全量
后台导出的字段 / 对象清单可能漏项，**不能直接当全量用** → 重连拉全量校准后再下结论。

### D06 明细合计 ≠ 汇总字段
主记录上的汇总（Rollup）字段是**权威值**。两边对不上，说明**明细没拉全**，不是汇总字段错了。
✅ 以汇总为准、回头补拉明细；**绝不反过来改汇总去迁就明细**。

### D07 明细字段读不到值
某些字段是**引用类型**，明细里读不到 → 改读主对象上的权威字段。
✅ 过滤条件一律用主对象字段，不要拿明细里的引用字段去筛。

## 4.5 ★ 关联边：用"列关联对象"工具打通链路

比逐个猜字段更快：`list-related` 类工具会返回**从该对象出发的所有关联边**（关联对象、关联字段 API、related list 名）。

典型业务链路形态（以销售类系统为例，具体字段以你的环境为准）：
```
线索 ──▶ 订单 ──▶ 回款
  │
  ├──◀ 跟进记录
  ├──◀ 外勤记录
  └──◀ 积分明细
```
**价值**：确认"上游对象能否直接取下游对象的数据"，这是很多统计口径的前提。
**一线索多订单时**，汇总口径（取第一个 / 合计 / 最新）必须向业务方问清，不能猜。

## 4.6 两套计算引擎（写公式必知）

很多平台有**两套独立的公式能力**，能力差异极大：

| 引擎 | 条件判断 | 日期函数 | 聚合 |
|---|---|---|---|
| **对象上的公式字段** | 通常支持 IF/AND/OR | 通常支持 YEAR/MONTH 等 | — |
| **报表层的计算指标** | **常不支持** | 受限 | 常仅支持四则与 SUM/AVG/COUNT |

✅ **可复用打法：把条件判断前移到对象公式字段，报表层只取结果做四则/筛选。**
（这条能绕开"报表层不能写 IF"的限制，实测有效。）

⚠️ 报表层的指标字段往往**只能选本对象的原始数值字段**；文本型公式字段只能做明细列 → 需要做跨对象去重时，通常要辅助对象或预计算。

## 4.7 写操作约束（先确认再动）

动手前先确认三件事，否则容易白做：
1. **哪些对象允许 API 直写，哪些禁止**（常见：核心单据对象禁写）
2. 禁止直写时，**替代路径**是什么（定时任务脚本 / 后台导入 / 流程后动作）
3. 脚本沙箱的**禁用语法**（常见：禁循环、禁某种注释、选项值要用专门函数取、空值需双判）

## 4.8 查询前先确认范围（约定）

拉明细前先向用户说明：过滤条件、预期数据量、**超过单页上限时的翻页策略**。
确认后再查——否则只取回第一页，结论是错的。
